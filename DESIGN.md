# Ouroboros — design

> A Claude Code plugin that learns from your sessions on its own: it saves memories and creates/refines skills without being asked, in the spirit of Nous Research's Hermes Agent, and shows on a local dashboard what it learned, how much that is being used and what it costs.

Status: v0.25.0 — every phase implemented (§13), plus the learning evaluation (§7.2), the v0.8 mechanism review (§7.4), the inbox reviewed in the conversation (§9.3), a dashboard that scales (§9.1: server-side paging and filters, the inbox grouped by project and file, page state in the URL, one project filter), a knowledge graph (§9.4, read-only, drawn with a vendored D3 subset since v0.13) and a session learning state shared by every review of a session (§6.5, v0.15) and one order of destinations for every path, with a home for preferences that matter for one topic or one kind of file (§7.5, v0.16), one instrument for the correction rate (§9.2, v0.17) and one project per repository in every table (§9.1, v0.18), a second mechanism review whose findings were each reproduced before being fixed (§7.6, v0.23), a control group for the correction rate (§9.2, v0.24), and a third mechanism review (§7.7, v0.25) whose findings were each reproduced before being fixed, among them the instrument itself: compaction summaries, forks and control sessions no longer enter the rate, and the Overview states its verdict with an interval and a usable baseline. Next: read that rate on real use, against the control (§7.4), before adding mechanisms; the instrument no longer counts compaction summaries, forks or control sessions wrongly, and its verdict says how wide the doubt is. Design decisions are summarized in [§12](#12-decisions).

---

## 1. Problem

Claude Code already has places to store learning — per-project auto memory (`~/.claude/projects/<proj>/memory/`, `MEMORY.md` index), personal skills (`~/.claude/skills/`, hot-reloaded), `CLAUDE.md` — but **nothing writes to them proactively**:

- native auto memory saves little, only 4 types (user, feedback, project, reference), and by design skips procedures and debugging fixes — exactly what Hermes turns into skills;
- there is no review loop: nothing native reviews a session and creates/patches skills;
- result: the user repeats the same corrections across sessions.

Hermes solves this with (a) explicit save triggers in its prompt, (b) a periodic background review, (c) skills as "procedural memory" refined through targeted patches and (d) hard size limits that force consolidation. Ouroboros reproduces this as a plugin.

## 2. Principles

1. **Three separate layers**: *capture* (deterministic hooks, no LLM, cheap, metrics only) → *reflection* (an LLM decides what to learn, on a cadence) → *curation* (deterministic rules decide where to write, dedupe, enforce limits, keep a ledger).
2. **No guessing user intent with heuristics.** Hooks never try to classify prompts; judging what is worth learning is always done by a model with the conversation in front of it.
3. **Every transcript segment is reviewed exactly once, and no review starts from nothing**: a per-session cursor records how far reviews have gone, and the session's learning state (§6.5) carries over what earlier reviews saved, queued and left open.
4. **Everything reversible**: every write has an origin, a diff and an undo.
5. **Hard limits** (like Hermes): fixed context budget; consolidate at 80%.
6. **Measure before learning**: phase 1 only measures, so there is a baseline to prove value against.
7. **Learn only from trusted sources**: user turns and verified outcomes — never from tool-provided text (web pages, command output), to avoid poisoning via prompt injection.
8. **Zero dependencies**: Node ≥ 22.13 (built-in `node:sqlite`), no `npm install`, no build step. Same behavior on Windows, macOS and Linux. The one third-party file is a D3 subset vendored as a static browser module for the graph (§9.4); it is committed, served by our own server and never fetched at runtime.

## 3. Architecture

```
Claude Code session
 ├─ SessionStart ─► inject the learning protocol (+ pending notices; with Claude Code's auto memory off,
 │                  a warning once per project and the index of the project memories Ouroboros saved)
 │
 ├─ CAPTURE (async hooks, no LLM, metrics only) ──────────► events.db (SQLite, WAL)
 │    UserPromptSubmit      turn counter
 │    PostToolUse(Failure)  tool calls; error → recovery (also inside subagents);
 │                          skill use; memory read; write to memory/skill (ledger)
 │    UserPromptExpansion   typed /skill (does not go through PostToolUse)
 │
 ├─ REFLECTION A — periodic in-loop review (Stop, synchronous)
 │    every N user turns, or after a turn that recovered from failures  →  {"decision":"block", reason}
 │    Claude reviews the segment since the last review with the `learn` skill
 │    and writes (Write/Edit); ends with a structured result line
 │
 ├─ SessionEnd (≤1.5 s) ─► enqueue session + spawn detached worker
 │    (a session that never got one — a crash, a killed terminal — is queued by the next
 │     SessionStart once it has been idle for 6 hours)
 │
 └─ REFLECTION B — end-of-session background review (detached Node worker)
      only the unreviewed tail (cursor → end) → compact digest
      → `claude -p` (Haiku, JSON schema) → proposals
      → CURATOR (deterministic): dedupe vs inventory → create | patch | skip
      → routing → limits → write → ledger → notice in the next session

Dashboard (node, 127.0.0.1) ◄── events.db + scan of memories/skills + transcript usage
```

### 3.1 Where things live

| Content | Location | Why |
|---|---|---|
| Facts relevant in every session whatever the task (who the user is, how they work, OS/shell facts) | the user's global `~/.claude/CLAUDE.md`, as additions under the section they belong to (§3.2) | Claude Code already loads it in every session; one global file instead of two |
| Preferences valid on every project that matter for one topic | `~/.claude/skills/learned-prefs-<topic>/SKILL.md`, a personal skill only the model invokes (§7.5) | Loaded when the topic comes up, not in every session |
| Preferences valid on every project that matter for certain files | `~/.claude/rules/learned-<topic>.md`, a user rule with `paths` (§7.5) | Loaded with the files it is about |
| Advanced config (routing, limits) | `~/.ouroboros/config.json` | Structures `userConfig` doesn't express well |
| Telemetry + ledger | `${CLAUDE_PLUGIN_DATA}/events.db` | Plugin state; persists across updates |
| Project facts | native auto memory (`~/.claude/projects/<proj>/memory/*.md` + `MEMORY.md`), resolved as Claude Code does: one directory per repository (its worktrees and subfolders share it), honoring `autoMemoryDirectory` (local, project or user settings), `CLAUDE_CODE_PROJECT_DIR_NAME` and, in cloud sessions that have one, `CLAUDE_CODE_REMOTE_MEMORY_DIR`; `paths.memoryDirFor` is the only place that computes it. Claude Code loads these only while auto memory is on (`paths.autoMemoryStatus`); when it is off, `SessionStart` puts the `MEMORY.md` lines of the memories Ouroboros saved for the project into the session context (§5) | Cooperates with the native mechanism instead of competing |
| Generic learned skills | `~/.claude/skills/learned-<name>/SKILL.md` | Apply to every project; prefix marks the origin |
| Project learned skills | target from the routing map (e.g. `**/acme-*` → `~/src/acme-skills/skills`) or the repo's `.claude/skills/`, in the repository's **main checkout** even when the session runs in a worktree | Don't leak into other projects; a worktree is temporary |

Ouroboros never writes to a CLAUDE.md (global or project) without the user's approval, even when the user asked for that change in the session: the request is queued and the user confirms it in the inbox (§7.3, autonomy). Since v0.24 the same holds for every file a person wrote: a rule file, and a skill Ouroboros did not create (§7.2, approval rules).

Every memory/skill Ouroboros creates carries in its frontmatter:

```yaml
metadata:
  origin: ouroboros
  id: lrn_01J...          # ledger key
  confidence: 0.6        # 0.3 tentative … 0.9 near-certain
  created: 2026-11-07
  trigger: periodic       # periodic | recovery | session_end | manual
```

### 3.2 Global facts

A fact valid on every project is proposed as an addition to the user's global `~/.claude/CLAUDE.md`, through the same path as any change to an existing file: the screen routes it there, the editor reads the whole file and places it under the section it belongs to (or finds it already covered), code validates the edit, and the change waits in the inbox for the user. When the user has no global CLAUDE.md (or an empty one), it reads as its title, since edits anchor on text (`paths.readKnowledgeFile`), and the file is written when the change is approved, through the ledger, so undo removes it again. Until v0.23 the file was created, outside the ledger, as soon as a global fact was proposed, even by a dry run.

Until v0.11 these facts lived in `~/.ouroboros/user.md`, a "global profile" Ouroboros wrote without approval and injected at `SessionStart`. It was retired in v0.12: it was a second global file next to the CLAUDE.md the user already curates, it repeated rules written there (two sources that drift apart and cost tokens twice), and it needed its own budgets, consolidation and rendering. Global facts are few (about one a week), so approving each costs little. On the first `SessionStart` of v0.12, `scripts/migrate.mjs` turns the profile's bullets into proposals for the global CLAUDE.md (the evaluation drops what that file already says), archives the profile learnings and moves the file to `~/.ouroboros/archive/`.

## 5. Capture (hooks)

All in **exec form** (`"command": "node", "args": ["${CLAUDE_PLUGIN_ROOT}/scripts/hook.mjs", "<event>"]`) — no quoting/shell issues on Windows. Capture hooks run with `async: true` (never block the session) and **only measure**; they never decide what is worth learning. Recursion guard: if `OUROBOROS_REVIEWER=1` (the reviewer's own sessions), every hook exits immediately.

| Event | Matcher | Mode | What it does |
|---|---|---|---|
| `SessionStart` | none (every source: `startup`, `resume`, `clear`, `compact`, `fork`) | sync | Creates the session row and records the source (`session_start` event; a `fork` is told apart from a resume in §6.3); brings the records in step with files deleted outside Ouroboros (§7.3, `reconcile`); injects the protocol (§6.1) + pending reviewer notices ("📝 since the last session I learned: …"). **Auto memory** (v0.25): it checks whether Claude Code loads auto memory here (`paths.autoMemoryStatus`: `CLAUDE_CODE_DISABLE_AUTO_MEMORY`, `--bare`, safe mode, a cloud session with no memory directory, `autoMemoryEnabled` in local, project or user settings; managed policy settings are not read). If it is off, it says so once per project (again only after it was seen on in between; `meta` key `auto_memory:<project>`) and adds to the session context the `MEMORY.md` lines of the active project memories Ouroboros saved there (newest first, at most 40 lines and 4,000 characters; native memories are not Ouroboros's to load). It leaves `options.json` for the dashboard from the hook's own options (the environment or the defaults, never the previous snapshot) plus that status. **Sweep**: queues the sessions whose `SessionEnd` never ran and that have had no event for 6 hours (§6.3), the reviews left to finish later, the orphaned queue, and respawns the worker if needed |
| `UserPromptSubmit` | — | async | Increments the turn counter. Claude Code also fires it for prompts nobody typed (a scheduled task, a background subagent reporting back, a message from another session) and gives the hook no way to tell, so the counter is an upper bound: the Stop hook checks it against the transcript (§6.2) |
| `UserPromptExpansion` | — | async | Typed `/skill` → `skill_used` |
| `PostToolUse` | `Skill` | async | `skill_used` (+ bumps `uses` if it is a learned skill) |
| `PostToolUse` | `Read` | async | Read inside a memory directory → `memory_read` |
| `PostToolUse` | `Write\|Edit` | async | Write to a memory or skill file → a `memory_write`/`skill_write` event (it also sees what Claude saves on its own). An observation only: the ledger, and so undo, covers curator writes (§7) |
| `PostToolUse` | `*` | async | Counts tool calls (per turn), recording a command as its first word or two, up to a shell operator or redirection (`ls -la && grep x` is `ls`; until v0.25 it was `ls &&`); closes an error → success sequence on the same target **within one user turn** as `recovery`, tagged with `agent_id` when inside a subagent (a failure in one turn and a success turns later are two events, not a working path; v0.20), with what happened in between: files written, other commands run, whether the command that worked is the one that first failed (v0.23, §6.2) |
| `PostToolUseFailure` | `*` | async | `tool_fail` with target (normalized file/command) and `agent_id` |
| `Stop` | — | **sync** | Reads the previous review result from `last_assistant_message`; decides whether to trigger a review (§6.2) |
| `SessionEnd` | — | sync, < 300 ms | Enqueues and spawns `review-worker.mjs` detached (`spawn` with `detached`, `windowsHide`, `unref`). It declares no `timeout`: a plugin hook cannot raise Claude Code's 1.5 s limit for this event, so the `5` it carried until v0.24 changed nothing |

Latency target: sync hooks < 150 ms (dominated by Node startup); async ones don't count.

## 6. Reflection

### 6.1 Injected protocol (Hermes's "system prompt", as session context)

Injected by `SessionStart`, short (~600 characters), so the plugin is self-contained and shareable:

> Ouroboros is active. Without being asked, save when you learn: a user preference, a correction of your approach, a project convention, an environment fact. When the user explicitly asks you to remember something, save it right away. Create or patch a skill when: you worked out a reusable multi-step workflow; you found the working path after errors; the user corrected your approach. Prefer patching what exists over creating new. Don't save what is derivable from the code/CLAUDE.md or what is ephemeral. When you save, say so in one line: "📝 learned: …". Details: skill `ouroboros:learn`.

Explicit "remember that…" requests need no detection: the protocol makes Claude save them immediately.

### 6.2 Reflection A — periodic in-loop review (Stop)

The `Stop` hook returns `{"hookSpecificOutput":{"hookEventName":"Stop","additionalContext": <script>}}` — which keeps the conversation going under the same loop protections as `decision: "block"`, without a hook-error notice — when:

- `stop_hook_active` is false (prevents loops), **and**
- `inloop_review` is on, **and** either
  - `review_every_turns` user turns have passed since the last review, or
  - the turn that just ended found a working path after failures: a `recovery` event (the same command failed at least `early_review_failures` times, then worked, here or in a subagent), and no review was requested in the last 5 user turns. Recoveries of file tools (an `Edit` that needed three tries, a `Read` of a wrong path) are recorded but do not trigger it: retrying until an edit applies is mechanics (v0.20). Since v0.23 two more look-alikes are left out (`hook.isWorkingPath`): **files were written between the failures and the success** (tests that fail until the code is fixed: red, edit, green is the job, and the lesson, if any, is in the code), and **the same command repeated with nothing else run in between** (a flaky service that answered on the third try). What remains is a command that worked after it was changed, or after another command was run. Reproduced before the fix: `npm test` failing twice and passing after two edits asked for a review, and in a real session a command that failed twice on a transient error cost a review of 77k cached tokens, a third of that session's tokens, to conclude there was nothing to learn.

  **Turns the user typed.** `review_every_turns` is counted by `UserPromptSubmit`, which also fires for prompts nobody typed (§5). When the counter says a periodic review is due, the Stop hook reads the transcript and counts the turns a person typed since the last request, the same way the reviews do (`transcript.isHumanPrompt`); if they are fewer, no review is asked for and the counter is set back by the difference.

  **A context too large to read twice.** An in-session review reads the whole conversation again, at least twice (loading the skill, then the answer), on the session's own model. It is recorded with its tokens and costs nothing against `monthly_budget_usd`, which only caps the calls Ouroboros makes itself, the cheap ones. So the limit is on what makes it expensive: when the context of the last model call is over `inloop_review_max_context` tokens (150k by default), the review is not asked for (`reviews.status = 'skipped'` with the reason), the cursor stays, and the stretch goes to the end-of-session reviewer, which reads a digest with a small model inside the budget.

  Until v0.8.0 the early trigger was a *long turn* (≥ 15 tool calls). Measured on 49 real sessions (308 turns), 32% of turns are that long, and only about a third of those worked through repeated failures: during feature work the early review fired every other turn, re-reading the whole context each time, mostly with nothing new to learn. A long turn alone is not a learning signal; a recovery is (the strongest procedural one, best captured while the context is fresh). Long turns are still recorded as a metric. Note: capture hooks are asynchronous, so a recovery on the very last tool call of a turn may land after the Stop hook and wait for the next review.

The request tells Claude to review **the segment since the last review only** and to finish with the result line. Claude Code prints the request to the user at every review, so since v0.22.3 it carries only what changes from one review to the next: the turn range, the commands that failed repeatedly before working (`significantRecoveries`: at least `early_review_failures` failures, never a file tool retried until it applied), the session's state in one line per entry, and the result line. How to review lives in the `learn` skill. The first screenshot of real use showed a 25-line request listing three single failures (a `git show`, a `Read` over the token limit, a `git branch`) and an entry whose title and text repeated each other. A review is also not requested while background agents or commands are still running (`background_tasks` in the Stop input): Claude stopped only to wait for them, and the review waits for the next stop. The result line:

```
[ouroboros] reviewed=<turns> corrections=<n> learned=<n> patched=<n>
```

On the next `Stop`, the hook parses that line from `last_assistant_message`, records it in `reviews`, and advances the session's cursor to the transcript position of the review. If the line is missing (Claude skipped the review), the cursor does not move and the segment falls to reflection B.

**A review that could not save keeps the stretch** (v0.25). The line can say `learned=0 patched=0` because nothing was worth keeping, or because saving failed: the `learn` skill was denied (headless mode, a permission rule), `curator.mjs` returned an error, or the Write of the payload file was refused. Until v0.25 both closed the stretch: the cursor moved, the end-of-session review skipped it, and an explicit "remember that, from now on" was lost (seen in a live session with the skill denied). Now the Stop hook reads the transcript from the request on (`hook.learnStepFailed`: an error result for the `learn` skill call, for a shell call that runs `curator.mjs`, or for any tool called after the skill started); if the result line claims nothing saved and a step failed, the review is recorded `skipped` ("could not save"), the cursor stays and a `review_unsaved` event keeps the first turn not saved. The next in-session review that is asked for starts at that turn instead of the last one, so it covers the stretch too, and the end-of-session review reads it if none comes. A review with no result line at all is kept the same way.

Cost is measured from transcript `usage` between the request and the next `Stop`. Most of the input is a cache read; the output is usually short. Measured end to end: a review with one save read ~64k cached tokens and wrote 187 output tokens. The next request comes `review_every_turns` turns later even if Claude skipped this one (`turns_at_last_review` moves when the request is made, the cursor only when the result line arrives). Subagent stops and `stop_hook_active` stops never request a review.

### 6.3 Reflection B — end-of-session background review

1. **Trigger**: `SessionEnd` (or an orphaned queued session found at the next `SessionStart`). A session whose `SessionEnd` never ran (a crash, a killed terminal, the hook cut short) used to stay with `queue_state` empty for ever: never reviewed, never measured, and out of the correction rate. Since v0.25 the next `SessionStart` takes a session with at least two turns and no event for **6 hours** as ended at its last event (`end_reason` says so, and a `session_end` event is recorded) and queues it; at most three per start, and a claim in one statement so two starts at once do not queue it twice. If it goes on later, its cursors make the next review read only the new part. A session whose last event is older than 7 days is left alone: learning from it now, with nobody watching, is what `/ouroboros:backfill learn` asks for approval for.
2. **Scope**: only the **unreviewed tail** — from the session's cursor to the end. A tail with a single user turn is skipped only when nothing ties it to the rest of the session: no earlier review, no `recovery` since, no open observation (one last turn after a review is often the correction of what that review saw).
   **What counts as a turn the user typed** (v0.25, `transcript.isHumanPrompt`). Two kinds of entry looked like one. After a compaction Claude Code writes the summary of the earlier conversation as a `user` entry with `isCompactSummary` (and `isVisibleInTranscriptOnly`) but without `isMeta` or `origin`: the plugin counted it as a turn (a `/compact` session with one typed prompt recorded `turns_reviewed = 2`), the digest showed it as `[USER #2]`, and the check for anchored evidence accepted it as a turn the user typed, although it is text the model wrote about tool output. It is neither counted, quoted nor shown as a turn now. And a **forked** session (`--fork-session`) gets a new id and a transcript that starts with a copy of its parent's: its cursors at 0 reviewed and measured the parent's turns again. Reviews and the instrument now start after the copy (`transcript.inheritedLines`, applied by the Stop hook and the worker whichever runs first): the entries timestamped before the fork started, up to its first own prompt (what the live check verified), and, when Claude Code marks a copied entry with `forkedFrom.sessionId`, up to the last marked one (which needs no start time, so it also serves a backfill).
3. **Digest**: `transcript.mjs` reduces the tail to user turns, assistant text, tool names and errors. The prompt adds the `recovery` events recorded since the last review, here or inside subagents (never full subagent transcripts; workflow agents are excluded entirely), and the session's learning state (§6.5). A tail that starts mid-session opens with the last 3 user turns before the cursor and what the assistant said between them, marked EARLIER (context only: not counted, not learned from alone). The assistant text right before a user turn keeps its end as well as its start, since that is where the question the user answers usually is. A tail over ~80k characters is first shrunk (tool calls, then long assistant text) and then split into parts at user turns, each reviewed by its own call with the USER numbering continued; the results merge into one review. Nothing in the middle of a long session is dropped (past 8 parts, the oldest middle parts are skipped and the review says so).
4. **Inventory**: titles + descriptions of the existing memories/skills in scope (so the model picks `patch` over `create`).
5. **Call**: `claude -p --safe-mode --model <reviewer_model> --output-format json --json-schema <schema> --tools "" --no-session-persistence --max-budget-usd 0.5 --system-prompt <short>`, `cwd` at `${CLAUDE_PLUGIN_DATA}/reviewer`, `OUROBOROS_REVIEWER=1`. Isolation is essential: a plain `claude -p` loads the user's whole environment (MCP servers, plugins, skills, CLAUDE.md) and a trivial call measured **US$ 0.78**; with `--safe-mode` and a custom system prompt the same call costs **US$ 0.0003**, and real session reviews cost US$ 0.002–0.008. `--safe-mode` also disables hooks, so the reviewer can't trigger the plugin; `--no-session-persistence` keeps its transcripts out of the user's projects.
6. **Output**: `{corrections, items: [{kind: global|memory|skill, scope?, memory_type?, title, text?, description?, body?, confidence, evidence, repeats?}]}`. Every item is recorded in `candidates` and goes through the **learning evaluation** (§7.2) before anything is written or queued; the reviewer sees only names and descriptions of what exists, so it never writes edits itself. A `duplicate` reinforces the existing learning (+0.1 confidence, max 0.9). `repeats` means "the user had to repeat something already saved" → *miss* metric (§9). If the evaluation fails (model error, budget), nothing is written: the items wait in the queue and the next queue check evaluates them.
   **Anchored evidence** (v0.20, narrowed in v0.23): principle 7 is checked by code as far as code can check it, which is that the cited user turn exists in what was reviewed, not that it says what the item says. So the rule is about who is behind an item: one that cites the user's own words may be written under the autonomy setting; one that rests only on what happened in the session (a command that failed and then worked, what a tool printed, what the assistant made of it) is evaluated like the rest and then waits for the user, whatever the autonomy. Until v0.22 a recorded recovery let through any item that cited no turn at all. For the same reason **a new skill proposed by this reviewer always waits** (§7.2, approval rules): a skill is instructions later sessions follow, written here by a small model from a digest that carries tool errors, with nobody watching.
7. **Notices**: created items become a notice; the next `SessionStart` shows it to the user (`systemMessage`) and tells Claude (context), then marks it delivered.
8. **Corrections** (v0.17; in every mode since v0.23): the worker first runs the correction-rate instrument (§9.2): one corrections-only call over what the session added since it was last measured (`sessions.measure_cursor`), independent of the review cursor. It runs even when the learning tail is skipped, and a failure never stops the learning review. The learning review still counts corrections for its own use; they do not enter the rate.
   **Reviews that do not finish** (v0.23). A long tail is reviewed in parts; when a later part fails or the month's budget runs out between parts, the review covers the parts it read: the cursor stops where the first unread part starts (`buildDigest.partStarts`) and the session is left `waiting`. The same when the model call fails outright, or the budget was already spent when the session ended. The next `SessionStart` queues waiting sessions again (once 30 minutes have passed and there is budget), at most three reviews per start; three failures and the session is given up, and the review says so. Until v0.22 a review that read one part of two moved the cursor to the end, and a failed or unaffordable review was never tried again, although the design said the work waited.
9. **Cost**: `total_cost_usd` and tokens from the result go to `reviews`. If the month's total ≥ `monthly_budget_usd`, the worker doesn't run. Measured end to end: a 23-turn session tail produced 3 corrections and 4 well-formed memories for US$ 0.008.

With `learning` off the worker runs in `measure` mode instead. `/ouroboros:backfill` uses `measure` by default (past sessions are counted, never learned from); `/ouroboros:backfill learn` reviews them oldest first as if Ouroboros had been active and sends every proposal to the approval queue.

**Phase 1 mode (`measure`)**: the same worker runs over the whole session: the instrument counts the corrections, and a second call returns candidate learnings, which are recorded and never written (one call returned both until v0.22; see §9.2). This produces the baseline. `/ouroboros:backfill` runs it over past transcripts (newest first, with a dry run and confirmation) so the baseline exists from day one instead of after 1–2 weeks.

### 6.4 `learn` skill script (used by A and manually)

- Quality filters (Claudeception + Hermes): **real discovery** (not just reading docs), **verified** (it worked), **reusable** ("would this help in 6 months?"), **not derivable** from code/CLAUDE.md, **not ephemeral**, **trusted source** (user turn or observed outcome).
- Count corrections: user turns that redirected the approach, explicit or implicit ("hmm, the test broke again", "I prefer the other way").
- Classify: fact → memory (native type `user|feedback|project|reference`; cross-project → an addition to the global CLAUDE.md); procedure → skill.
- Always check what exists first; prefer a targeted patch.
- Memory format identical to native auto memory (frontmatter `name/description/metadata.type` + a line in `MEMORY.md`), plus `metadata.origin/id/confidence`.
- End with the result line (§6.2).

### 6.5 Session learning state (v0.15)

A review used to see only its own segment. With the periodic review every N turns, the end-of-session reviewer almost always got a short tail out of context: a first line like "1. yes 2. no" answering a question before the cursor, no idea what the review ten turns earlier had saved, and so no way to tell a refinement from a new fact. A learning that spans the boundary (a correction at turn 9, confirmed working at turn 12) was judged twice with half the evidence each time.

The state is what carries over (`scripts/session-state.mjs`), per session, read by every review:

- **What earlier reviews did**: each save (from the ledger, by `session_id`), each proposal waiting, in conflict, dropped, suggested or rejected (from `candidates`), with a ref, the file and the text. Derived from tables that already exist; nothing is stored twice.
- **Open observations** (`observations` table): something worth keeping that was not settled when a review ran (not verified yet, said once). The in-session review records them through the `learn` skill's apply step (`"open"`, closed with `"resolve"`); every later review of the session sees them, and the session's last review closes them all.

How each review uses it:

- **Periodic review (A)**: the Stop request lists the state and tells Claude to patch what the session already saved instead of creating, and to pass unsettled things in `"open"`. `curator.mjs inventory --session` prints it too, which is what survives a compaction.
- **End-of-session review (B)**: the prompt carries the state; an item may set `"refines"` to a ref. A refinement the screen keeps goes to the editor of that file (§7.2), which folds it in, instead of becoming a second memory.

Kept on purpose: the cursor and the exactly-once rule (state, not re-reading, is what connects segments), and both triggers.

## 7. Curation and write policy

**Single writer.** Every Ouroboros write goes through `scripts/curator.mjs` (`apply`, `undo`, `forget`, `inventory`). In-loop, Claude calls it from the `learn` skill (proposals as JSON on stdin); in phase 3 the background worker calls the same `apply` in-process. Claude's own direct writes to memory files (native auto memory) are still observed by the capture hooks, but only curator writes carry a ledger entry and can be undone.

Proposal item: `{ op: create|patch, kind: global|memory|skill, scope, memory_type, section, project_dir, name, title, description, body, text, target, old, new, append, confidence }`. A `global` fact (and a `memory` with `scope: global`; `profile` is accepted as the pre-v0.12 name) becomes an `append` to the global CLAUDE.md under `section`, refused as `duplicate` when a line of that file already says it, merged when the same fact already waits for approval, and queued like any CLAUDE.md change. A patch targets a learning id, an absolute path of a memory, skill, rule file or CLAUDE.md (a path under `~` is resolved first, so it meets the same approval rules: until v0.22 `~/.claude/CLAUDE.md` passed the check that only looked at absolute paths, and was written without approval), or a name, and either replaces an exact `old` fragment with `new` or replaces the `description` (memory patches also update the `MEMORY.md` line). Native skills and memories can be patched (refined) too; they are then tracked with `origin_session = 'native'` and don't count against the learned-skill budget. Routing rules may set `linkInto` to create a directory link (junction on Windows) so skills kept in a separate repo load from `~/.claude/skills`.

**The memory directory is Claude's word too** (v0.25). A payload may carry `memory_dir`; `curator.mjs apply` (which the `learn` skill pre-approves) took it as given, so a "memory" could be written into `~/.claude/rules/` (loaded in every session) or a project's `.claude/rules/`, with no approval, in every autonomy mode. Now `checkedMemoryDir` keeps it only when it is the directory `memoryDirFor` computes for the payload's own project; any other is ignored with a warning, the result says `memory_dir_ignored`, and the memory goes to the computed one. What waits for approval is stored with the clean payload.

Duplicates are **not** merged automatically: the curator answers `duplicate` with the existing target and Claude re-submits a patch — the model merges, the curator guards.

Default: **`autonomy = auto`** (like Hermes). Consequences:

- A proposal that passes the filters is written directly; one-line notice in the session (A) or in the next session (B).
- **Undo is mandatory from the first write**: `/ouroboros:undo` and a dashboard button revert using the ledger diff. When the file changed after the write (the user's edits, another learning), undo reverts only the lines that write changed, located by a line diff with surrounding context, and keeps the rest; it refuses only when those very lines were edited since. Each applied changeset records its ledger batch, so the dashboard can undo one change exactly (Activity, Proposals, *Undo change*); what the user undoes joins the past rejections the screen sees.
- Low confidence (< 0.5) still goes in, but is the first to be archived if unused.
- `hybrid`/`queue` modes are there for users who want to approve first (the inbox, §9.1 and §9.3).

Curator steps (`curator.mjs`, deterministic):

1. **Validate** schema and size.
2. **Dedupe**: lexical similarity (trigrams, Jaccard ≥ 0.6) against the scope's inventory → turns `create` into `patch` or drops it.
3. **Route**: `global` scope → the global CLAUDE.md or `~/.claude/skills/learned-*`; `project` → the project's native memory or `routing[].skillsDir`; no rule → the repo's `.claude/skills/`.
4. **Limits**: a write that takes a budget past 80% is flagged, and the daily maintenance (`maintenance.mjs`, §7.3) trims it: it archives the weakest items (merging and shortening were planned and never built; they wait for the correction rate to show the loop's value). A write past 100% is refused as `over_budget` until something is consolidated.
5. **Write** atomically (temp file + rename) and record it in `writes` with the diff.
6. **Notice** queued for the next session.

### 7.1 The learning rubric

A healthy self-learning loop needs one, explicit definition of "worth remembering", applied the same way by every path that writes, for every user and project. It lives in `scripts/rubric.mjs` and is injected verbatim into the end-of-session reviewer, the knowledge check, and the `learn` skill (`test/rubric.test.mjs` fails if the skill drifts); the session protocol carries a one-line version. The nine rules:

1. **Behavior change** — would the assistant act differently next time without it? (drop default behavior, generic practice, preferences already configured, alternatives to guidance that already handles the case)
2. **Standing** — a rule the user stated as lasting, repeated, or a recorded decision; not a one-time request.
3. **Not derivable** — absent from code, config, tests, git history and docs.
4. **Verified** — worked or stated by the user; what the project executes (triggers, commands, parameters, config) is ground truth, comments are not, and an observed outcome beats a comment.
5. **Durable** — no status, to-dos, counts, timings, issue numbers, finished work.
6. **Owner** — add to the skill/rule/doc that owns the topic, else a project memory, else a global fact; never a second copy.
7. **Correct the stale** — ground truth or an explicit change of rule fixes the outdated text; a one-off request never overturns a standing rule.
8. **Fix at the source** — a workaround for a fixable defect (a generated file not ignored, a broken script, a missing config line) becomes a suggested fix for the user, not knowledge.
9. **Trusted, no secrets.**

These came from reviewing real proposals by hand, item by item, and turning every judgment into a rule. The rubric is project-agnostic; everything user- or project-specific comes from the indexed knowledge.

### 7.2 Learning evaluation

Every proposal from a Claude-less path (end-of-session reviewer, learning backfill, approval queue) is evaluated before it is written or queued (`scripts/evaluate.mjs`). A change to an existing file is written only when two independent judgments agree: the **screen** and the **editor**. A new memory or skill has no file for an editor to read: it is written when the reviewer proposed it, the screen kept it and the curator's checks (dedupe, budgets, approval rules) pass. A proposal the screen returns no verdict for is never written: it is screened once more and then waits for the user (v0.14.2; until then it was treated as kept).

**Why it is built this way.** During development, the first learning backfill (60 proposals from 30 past sessions) and two rounds of hand review showed where single-pass judgment fails: a third of the proposals were already documented; the same fact arrived in two languages, or aimed at two different owners; one-off requests looked like rules; and, most of all, a proposal judged from *excerpts* of a file can repeat what the rest of the file already says, contradict another line of it, or contradict the code. Each proposal was also resolved alone, so two learnings could make conflicting edits to the same file, and an edit computed on one day was applied blindly days later.

**Stages:**

1. **Screen** (`scripts/triage.mjs`, one isolated call per 12 proposals). Inputs: the rubric; BM25 excerpts of what Claude already knows (`scripts/knowledge.mjs`: global and project CLAUDE.md, `.claude/rules`, skill bodies **and their reference files**, memories); sources of truth (CI workflows, manifests, deploy config); past rejections; and the **owners map** (every skill and rule file with description, sections and reference files). Verdicts: `drop` (with a rubric reason), `merge`, `keep` (new item, rewritten), `route` (the topic has an owner file: return the owner and the knowledge as one self-contained *claim*; the screen never writes edits), `fix` (a fixable defect: becomes a **suggested fix**, nothing is learned). Any verdict can flag a **stale owner** a source of truth contradicts, which becomes a correction claim for that file — only when the flag cites a file that really is a source of truth (checked by code: it exists and is not a knowledge file); a user preference can never flag documentation as outdated. A final pass merges duplicates across batches *by fact, not by target*, so the same fact sent to two owners is kept once. **The owner a `route` verdict names** is resolved by code (`knowledge.resolveRouteOwner`): only a file of that project's knowledge set can be one (its CLAUDE.md files, rules, skills and memory directory, plus the user's own global files), whatever its path looks like; a bare name that matches several files ("CLAUDE.md", with a global and a project file) goes to the one inside the project's root, else the one directly at it, and anything still ambiguous is not guessed. When no owner resolves, nothing is created: the learning waits for the user with the reason. Until v0.25 it was written as a new item, duplicating what the owner already said, and a target was checked by the shape of its path only, so another project's `MEMORY.md`, any `CLAUDE.md` on disk or `node_modules/…/skills/x/README.md` could be named. The stand-in memory of a claim (below) is left out of the excerpts its own screen sees, as the editor's already was: otherwise the screen found the stand-in, called the claim covered and dropped it while its stand-in stayed active.
2. **Ground** (no model). Identifiers the claims name — code spans, paths, dotted names, CONSTANTS, camelCase, `--flags` — are looked up with `git grep` in the tracked code and config of the project's repos (markdown excluded). "Not found" is evidence too, but only when the lookup was made: outside a git repository, with git missing, or on a timeout or overflow, the identifier is reported `could not check` (v0.25), which the editor is told is no evidence either way. Until then it read "not found" and was taken as a reason to call a claim contradicted. A file that is on disk exists, tracked or not.
3. **Edit** (one isolated call per owner file). The editor reads the **whole file** (outline plus related blocks, verbatim, when it is over 40k chars), **every learning pending for that file** (the new ones and those already waiting in a changeset), the grounding, the rubric, and what **other** files say on the same topics: knowledge the assistant already reads (a learning another file covers is `covered`, never copied) and related sources of truth (project evidence). Per claim: `covered`, `contradicted` (by the project), `adds`, `corrects` (the file is wrong; shown by the project or by the user explicitly changing a rule — a one-time request never overturns a standing rule), `conflict` (with another claim or the file, unsettled). Then **one coherent set of edits**: exact `old` fragments copied from the file, replaced by `new`; additions anchored after the line where they belong, in the file's style and language; only `corrects` edits may remove text; text elsewhere in the file that says the opposite must be fixed in the same set. Disagreements are settled by project evidence, then recency.
4. **Validate** (`scripts/changesets.mjs`, code, never the model). Each edit applies only if its fragment occurs exactly once and it leaves the frontmatter and headings intact; the text it **adds** holds no secret (checked on the added text, not the whole file, so a file that already contains something secret-looking does not let a new secret through); the whole set grows the file by at most 6,000 chars; an edit that no `adds`/`corrects` learning justifies is dropped. An edit is an **addition** only when it adds whole lines: every line the file had is still there, in order and unchanged (`textdiff.isInsertion`, on the file before and after, trailing whitespace aside). Anything else rewrites what the file says (even one word: "Run X" to "Never run X"), so it is a **correction** whatever the editor called it. Until v0.22 the test was that the old fragment survived inside the new text, which words put in front of it or after it also pass: "run the tests" to "do not run the tests", or a clause appended to a rule, counted as additions and were written without approval. A correction: is marked `corrects`, may remove at most 800 chars, and waits for the user. A changed `description` is always one (a one-line value has no lines to add). Learnings whose edits all fail are dropped with the reason.

   **Structure counts too** (v0.25). Whole new lines can still change what existing lines say through the markdown they join, so `isInsertion` also refuses three cases: an indented line glued under an existing rule ("- Always deploy from main." + "  except on Fridays, when you must never deploy" is one item to every reader), a line inside an existing fenced code block (a command run as part of those steps), and a list item added to a list that an existing line introduces with a colon ("Never:", also `**Never:**`). The append path starts a paragraph of its own when its text would land under a list item. New sections, new items at the end of an ordinary list, sub-items with their own marker and new fenced blocks remain additions; the cases that are not seen are stated in §7.7. The validator also keeps headings as they were (the text of a heading cannot change, `## Never do` to `## Always do`, and a `#` comment inside a fenced block is not a heading), sees the frontmatter of a file with a byte-order mark or with spaces after the opening `---`, matches a fragment whatever line ending it was written with and gives what replaces it the file's own (a CRLF file no longer ends up with mixed endings, after which undo refused), and looks for secrets in the lines the edit leaves in the file as well as in the text it adds (a fragment can be harmless while the line it completes, "password: " plus a value, is not). A first preference is checked on every field that carries text.

**Conflicts go to the user.** A learning the editor judges `conflict` is never dropped: it waits in the dashboard's *Conflicts — you decide* section (and the session-start notice says so). "It is a new rule" marks it `confirmed`; it then skips the screen and goes to its file's editor, which must write it (as a correction of what the file says). "Keep the current rule" rejects it, which also feeds the past-rejections index. A conflict the user settled as a new rule is never dropped afterwards: when the editor's edit does not apply, it comes back as a conflict with the reason (v0.25; it was dropped as "not written" before) and the user decides again.

**Changesets.** The result is at most one pending **changeset per file**: the validated edits, the learnings they implement, and the hash of the text they were composed against. A new learning for that file recomposes the changeset with everything pending, so changes never conflict. Approval (dashboard, `approve`) re-applies the edits to the *current* file: if the file changed but the fragments still fit, the change lands on top of the newer version; otherwise the changeset goes **stale** and the next queue check composes it again. Rejecting one learning of a multi-learning changeset recomposes the rest without it. A change no learning waits in (each was decided on its own) is closed, not written: approving it used to save lines nobody had approved (v0.25). A composition identical to the one already waiting (same text, edits and learnings) keeps its id, so the entry the user may be reading stays. Applying goes through the curator's ledger, so `undo` works as for any write. New items (`keep`) still go through the curator's create path (dedupe, budgets, routing); a create that turns out to duplicate an existing memory or skill becomes a claim for that file, so the editor folds in only what is new.

**Patches Claude writes in session** (the `learn` skill, which reads the files itself) skip the screen and editor but not the validation: they pass the same `applyEdits` rules, and one that rewrites text (or replaces a description) is a correction that waits for the user even in `auto`. When they need approval they join the file's pending changeset if the edits still apply together; if not, the pending changeset goes stale with the new learning attached and the editor composes both (a file never has two pending changes).

**One evaluator at a time.** Sessions end in parallel, the daily maintenance runs on its own and the dashboard can ask for a check, so the evaluation is a **queue with a single consumer**. A review records its proposals as `pending` and calls `drainQueue`, which takes a lease in the database (`meta`, 30 min expiry for a crashed holder, renewed before each model call so a long drain never loses it while it runs) and evaluates until nothing waits, including what other processes queued meanwhile, then looks once more after releasing it. A process that finds the lease taken leaves its work for the holder. A live session's proposals are evaluated together, so its notice says what happened to them. Before a composed changeset is saved, the database is checked again: if the user approved or rejected a change to that file while the model was running, the composition is discarded and redone. A changeset is written under the write lock, and only if the file still holds the text its edits were applied to.

**What the queue re-checks after a model call** (v0.25). Until then only the status of the previous changes was looked at, so two things could be wrong after a slow call. Now the result is saved in one `BEGIN IMMEDIATE` transaction and only if nothing it was composed from moved: every learning is in the state it was taken in (a row the user rejected meanwhile is left as rejected, in the screen and in a failing editor call too), the changes it replaces have the status they had, no learning has joined them since (a live session's patch attached while the editor ran is kept), no other change for the file is pending, and the file still has the text the editor read. Otherwise the new learnings are composed again next round and nobody else's row is touched. A lease that passed to another process during the call (this one was suspended past the expiry) stops the drain after the call is recorded (`LeaseLost`) and leaves the rows to the new holder; a failed renewal used to be ignored.

**Bounded retries.** A failed screen or editor call is tried again at the next drain, not in the same one, and a proposal the screen leaves unanswered or an editor that returns no verdict for a learning is tried at most twice (`MAX_SCREEN_MISSES`, `MAX_EDITOR_MISSES`): then it waits for the user with the reason, and the card says why. Before, the queue tried again without limit, four screen calls and four editor calls per drain for ever, and one failing group held back a good proposal from another project. A group that fails is skipped for that drain and the others go on.

**Why the model writes the edits but code applies them.** A model rewriting whole files would silently lose content, drift in style and, edit after edit, degrade the text. A model is still the right author for *where* and *how* a fact belongs in a document, and for noticing that a line elsewhere now contradicts it. Exact-fragment edits keep both: the model decides and writes, the code guarantees what can change, the user sees a diff, and the ledger undoes it.

**Approval rules**: corrections, any change to `.claude/rules` or CLAUDE.md, and (v0.23) a new skill proposed by the end-of-session reviewer or an item of its that cites no user turn (§6.3), always wait for the user, whatever the autonomy. New skills Claude saves in session, with the conversation and the user in front of it, follow the autonomy setting. **A skill a person wrote is theirs** (v0.24): until then a line could be added to it in `auto` without asking, a tracked project skill included, while the same line for the CLAUDE.md next to it waited. Now any change to a skill Ouroboros did not create waits, however the patch names it (a path, the skill's name, a learning id: `apply` resolves the target to its file before any check), and whoever Claude says asked. It costs nothing in what Claude knows: the addition is active meanwhile as a project memory (below), for a personal skill in the project where it came up. Two exceptions, both decided by code from the ledger and never by a proposal: a rule file Ouroboros created for learned preferences takes additions like any learned file (§7.5), and, since v0.21, **a memory Ouroboros wrote and nobody edited since may be refined without approval in `auto`** (`ownUntouched`: Ouroboros created the file, and its text is exactly the result of Ouroboros's own last write). The "any rewrite waits" rule exists to protect what a person wrote; a memory saved ten minutes earlier by the same loop is not that, and making the user approve each refinement of it was the repetitive manual step the session state (§6.5) had just made common. One hand edit and the file is the user's again; in `hybrid` and `queue` nothing changes; conflicts still go to the user; the ledger undoes it. **For good** (v0.25): `ownUntouched` now follows the file's whole history in the ledger, not only its last write. Each write must have started from what the previous one left, from the write that created the file; until then an Ouroboros addition on top of a hand edit made the file "untouched" again, and the next correction rewrote the user's line without asking.

**A held learning stays held** (v0.25). The rule that an item citing no user turn, or a learning backfill, always waits was kept per run: a change recomposed with a later, anchored learning for the same file took the autonomy of the group that arrived last, and both were written ("waiting for approval: Held item" was followed by "updated: Held item; Anchored item"). Each claim now carries its own autonomy, and a change takes the strictest among its learnings; the stand-in memory of a held learning is not written either. The cost is stated in §7.7: the anchored learning waits with it.

**Learn now, promote on approval** (v0.22). Waiting for approval used to mean Claude did not know the rule until someone opened the inbox. Now a pure addition routed to a **project's** CLAUDE.md or rule file, or (v0.24) to a skill the user wrote, is also saved at once as a project memory (`learnMeanwhile`: a `feedback` memory, under the same autonomy rules as any new memory, so nothing is saved in `queue`). The waiting change becomes a question about where the rule lives, not whether Claude knows it:

- **approve**: the line is written and the stand-in memory is archived (`retireInterim`);
- **reject**: the memory stays (not in the shared file, still known); `/ouroboros:forget` removes it;
- **the editor finds the claim contradicted** by the project: the stand-in goes with it;
- **the stand-in is refined** (a later session adds an exception; Ouroboros may rewrite its own memory, above): the waiting claim takes the memory's current text and its change is composed again (`syncInterim`), so approving later never writes the older wording.

The stand-in is excluded from what the editor sees as "another file that already says it" (it would drop the very claim it stands in for), and since v0.25 from what the screen sees too. Not for corrections (they change what a file says; there is nothing to save beside it), nor for a change that is held for the user (above), nor for a fact proposed straight for the global CLAUDE.md (no project memory can stand in for it; narrower global facts already have a home, §7.5). Since v0.25 there is one exception, a rule promoted to the global CLAUDE.md because a second project taught it (§7.3): that line waits, and used to leave nothing active in the second project; now the project memory is saved as well and stands in for it the same way (one stand-in per project that learned the rule while it waited). **Undo brings them back**: approving retires the stand-ins and remembers which (`retired`); undoing the change that wrote the line restores them, so the rule is never in neither place. **Approving writes what the card showed**: a queued project memory is no longer turned into a line for the global CLAUDE.md at approval because another project saved something similar meanwhile (the user's "yes" created that file), and an approval the curator refuses (the index is full, the file changed) leaves the entry waiting, with the reason, instead of consuming it as `approved_over_budget`. The session-start notice reports such a learning as learned, once, with where it is proposed to go. Simulated again on the same eight sessions: the first project had its rules active from the first session, and the exception stated three sessions later corrected the stand-in memory and reached the pending CLAUDE.md change.

**The description follows the body** (v0.21). Edits could not touch the frontmatter, so a refined memory kept its old one-line `description` and its old line in `MEMORY.md`, the very line a rule acts through (§7.3). The editor may now return a new `description` for a memory whose body its edits change; it becomes a description edit (`applyEdits`: the only frontmatter value that may change, checked by comparing the rest of the frontmatter; always a correction), and applying it rewrites the `MEMORY.md` line in the same ledger batch.

**Measured** on the same 60 real proposals: 26 dropped, 1 merged, 4 suggested fixes, 6 new items and 10 changesets (17 learnings) waiting, among them 1 correction and 3 conflicts detected and handed to the user; US$ 0.09 per full pass. By hand review, about 4 of the ~23 survivors are debatable (v0.6: about 10 of 26). Known gap: a stale line elsewhere in an owner that no claim names is not noticed (e.g. a skill saying a page has no route guard after one was added); a periodic audit of owners against sources of truth is the next step.

**Run against the real model (v0.20.1).** Until v0.20 every mechanism added since v0.14 had only been tested with a stand-in model. Three runs, all in throwaway directories: the synthetic suite (15/15 with the destinations in the prompts); two end-of-session reviews of one real session, with Haiku and with Sonnet; and a controlled session with known right answers, reviewed in two parts, plus the same requests typed into a live session with the plugin loaded. In the controlled session all five outcomes were right: a project rule became a project memory, a commit preference was added to the existing commit skill, a code-review preference became `learned-prefs-code-review`, "always reply in Portuguese" waited as a change to the global CLAUDE.md, and the tail's exception to the deploy rule came back with `refines` and became a correction of that memory instead of a second one. What the runs showed that tests could not: the owner check's score threshold (above); the `learn` skill's heredoc tripping Claude Code's command check, and its grep of global files being blocked outside the working directory (the skill now uses `--file` and leaves global files to `has_owner`); the corrections instrument disagreeing between models on borderline turns (a question, a numbered answer); and, on the real session, Haiku not re-proposing an item the first review had dropped as unconfirmed although the tail confirmed it. The refinement then waited for approval and left the memory's `description` and `MEMORY.md` line with the old wording; both were addressed in v0.21 and confirmed on the same run.

**Simulated use (v0.21.1).** Eight sessions written to look like real work (two projects, one sandbox so knowledge accumulates: a correction with a derivable fact and a one-off, a session with nothing to learn, a web page telling the assistant to "remember" something plus a pasted key, a repeated correction with an exception added, a working path found after failures, the same rule in a second project, an explicit change of a written rule, a session in Portuguese), reviewed end to end by the real reviewer, screen and editor, and three live sessions with the plugin loaded. What held: nothing was learned from the web page, the key was never stored, the one-off and the derivable fact were dropped, the empty session produced nothing, preferences valid everywhere became topical skills at once, the rule change became a correction of CLAUDE.md that waits, the Portuguese session was saved in English, and the Stop request made Claude review in session, use the session state and close with the result line (46k cached tokens read, 91 written). What it exposed and v0.21.1 fixes: the editor could not tell which of two same-day sessions was later (claims carried a date, not a time) and called the user's own exception to a rule a conflict; a working path the user confirmed was dropped as "unverified" because an environment variable it names is not in tracked files (absence is evidence only about what files contain); a one-turn tail that was skipped still moved the cursor, so a session continued one turn at a time (resume, headless calls) was never reviewed; and the session-start notice repeated "CLAUDE.md (1 change)" per review without saying what waits. It also showed that in both paths a rule about one project is routed to that project's CLAUDE.md, whose additions always wait for approval: the first project had four sessions' worth of rules in one pending change and nothing active, and the user had to repeat a correction that was sitting in the inbox. v0.22 answers it (below).

**Measuring it.** `node scripts/eval.mjs --synthetic` runs the evaluation with the real model on a fake project with known right answers (`test/eval/synthetic.json`: covered, contradicted by code, stale owner, duplicates across owners, one-off, skill reference owner, fix at source, conflict pair, derivable, new memory, a one-time request against a standing rule) and prints a score (12/12, about US$ 0.01 per run). `--replay` re-evaluates the proposals the user approved or rejected, on a copy of the database, and reports agreement. `--sessions` scores the two calls that read sessions, which the synthetic suite does not reach: the corrections instrument (which user turns it counts) and the end-of-session reviewer (what it proposes), on cases taken from mistakes seen in real and simulated sessions (`test/eval/sessions.json`: a question, answers to what the assistant asked, the user changing their own mind, a concern as pushback, Portuguese; nothing to learn, a web page's instruction and a pasted key, a planning conversation, a confirmation of something an earlier review left unconfirmed, preferences that need a topic). Each case runs several times, because the same call can answer differently: v0.22.0 scored 31/36 (it counted the user revising their own instruction as a correction, 0/3, and saved a "lesson" from a planning conversation, 1/3); with the definition of a correction and two rubric rules tightened, 36/36, at about US$ 0.02. Run all three after changing the rubric or a prompt.

Dropped, merged and suggested items stay visible in the dashboard with their reason and can be restored; a restored proposal is not screened away again (v0.25; it was dropped by the next drain): like a confirmed conflict it goes on as a new item, with the curator's checks and the autonomy setting still applying, and an owner the screen finds is still used. Learnings are written in `learning_language` (`en` by default, `pt-BR` or `auto`); edits to existing files follow that file's language.

### 7.3 Lifecycle

```
proposal ─► active (conf. 0.3–0.9) ─► reinforced (+0.1 per use) ─► kept (the user pins it: never archived automatically)
                     │
                     ├─► archived (60 days unused, or merged into another)
                     ├─► reverted (user undo; counts as a negative signal for the reviewer)
                     └─► removed  (its file was deleted outside Ouroboros; back to active if the file returns)
```

Archive = move to `~/.ouroboros/archive/` (out of context), never delete. The archived file is named `<date>-<learning id>-<name>` (since v0.25; two files with the same name archived on the same day used to overwrite each other).

How each transition happens (phase 4):

- **Reinforcement**: the first read of a learned memory or use of a learned skill in a session adds +0.1 (hooks); a background review that rediscovers an existing item adds +0.1. Cap 0.9. Confidence only matters for what maintenance may archive (below), so the dashboard does not ask the user to "confirm" a learning; it offers **Keep** instead (`learnings.pinned`): a kept learning is never archived for being unused or trimmed for budget. Keep is shown only on learnings maintenance could archive (memories and skills Ouroboros created), with the date it would happen; files Ouroboros only added to (a skill, rule or CLAUDE.md it did not create) are never archived and cannot be: `forget` refuses them, since archiving would remove the whole file, and their changes are undone one by one instead.
- **Merge on rediscovery**: when the background reviewer's item is a `duplicate` of a memory or skill file, it becomes a claim for that file and the editor (§7.2) folds in only what is new (usually nothing: `covered`).
- **Promotion**: a `feedback`/`user` memory similar to one already saved in *another* project becomes a proposed addition to the global CLAUDE.md instead of a copy. Since v0.25 the project that taught it second keeps the rule active meanwhile, as a project memory that stands in for the waiting line (§7.2); until then the rule worked where it was first learned and was unknown where it was learned again. Approving the line retires the stand-ins and undoing it brings them back.
- **Files deleted outside Ouroboros** (v0.23, `curator.reconcile`). The ledger knows what Ouroboros wrote, but the files are the user's: they delete a memory by hand, and Claude Code tidies its own memory directory. Until v0.22 nothing noticed. The learning stayed `active`: shown as learned in the dashboard, counted against the skill budget, failing to archive at every maintenance (`forget` threw "file not found"), its line in `MEMORY.md` pointing at nothing in every session, and nothing kept the next review from saving the same thing again. Now every `SessionStart`, the daily maintenance and the dashboard (at most every 15 s while open) compare the active learnings with the disk. One whose file is gone becomes `removed`: out of every count and budget, labelled *File gone* in Knowledge › Learned, with one notice in the next session of its project. When Ouroboros created it, its dangling `MEMORY.md` line is taken out through the ledger (op `cleanup`), and the deletion counts as a rejection for 180 days: the screen sees it among the past rejections (`triage.rejectionDocs`), and in session the curator answers `was_removed` to a new item that says the same, which Claude re-submits with `removed_checked` only when the user asks for it or it adds something (the same pattern as `duplicate` and `has_owner`). Code cannot tell who deleted the file, and does not need to: if Claude Code merged the memory into another, the knowledge check finds it covered there; if the user threw it out, it is not saved again unasked. One case is not a deletion at all: a file in a git working tree (a project skill committed on one branch) is simply not there on another. Such a learning still leaves the counts while its file is gone, but silently: no notice, and nothing held against saving it again (`curator.inWorkingTree`). A file that comes back (a restored backup, a drive mounted again, the branch checked out again) makes the learning active again, as long as it is the same file (it still carries the learning's id and no newer learning took its path). `forget` and `undo` of something already gone bring the record in step instead of failing, and a stand-in memory (§7.2) the user deleted is never written a second time.
- **Daily maintenance** (`review-worker.mjs --maintain`, started by `SessionStart` at most every 20 h, results shown as notices). The worker claims the day's run itself, in one statement (`maintenance.claimRun`). Until v0.22 the hook wrote the time of the run before starting the worker, the worker then found that maintenance "ran recently" and left: decay, trimming, pruning and the retry of proposals whose evaluation had failed never ran outside the tests, which all called it with `force`. It does:
  - *decay* — archive Ouroboros memories/skills unused for `archiveAfterDaysUnused` days whose confidence is below 0.7 (native items, CLAUDE.md files included, are never touched). "Unused" means never read (a memory file) or invoked (a skill), which is a real signal only for what is looked up on demand. A `feedback` or `user` memory states a rule, and its line in `MEMORY.md`, loaded in every session of the project, already says it: Claude follows it without opening the file. Until v0.18 those rules, saved at the default confidence of 0.6, were archived after 60 days precisely when they worked. Since v0.19 they are exempt from decay (`maintenance.actsThroughIndex`) and count as used when a budget is trimmed;
  - *trim* — memory indexes and learned skills past `consolidateAt` archive their weakest items (`confidence × (1 + log2(1 + uses))`) down to 70%. Nothing is merged or shortened: consolidation is archiving, by code, with no model call.
- **Misses** (v0.19): when the user had to repeat something already saved, the learning's `misses` goes up, once per session. Two detectors: the end-of-session reviewer naming the saved item (`repeats`), and, since v0.22.1, code comparing each correction the instrument quotes with what every learning saved before the session says (`missFromQuote`: several distinct terms in common and at least half of the shorter side). The second exists because in simulated use the reviewer left `repeats` empty on a plain "I already told you". It never lowers confidence (the user cares about it; what failed is the text). From the second miss on, one suggestion goes to the inbox to reword it so it says when it applies, or to move it to the file that owns the topic.
- **Autonomy** (`auto` | `hybrid` | `queue`): proposals from Claude (`actor: inloop`) or the reviewer (`background`) that need approval are stored as `queued` candidates with their full payload; A request Claude labels as the user's (`actor: requested`; the `learn` skill's `"actor": "manual"`) skips the autonomy setting only: corrections and changes to rule files or a CLAUDE.md still wait, because the label is Claude's own and must not be what lets them through (v0.14.2). Only a decision the user makes on an entry (inbox, dashboard: `actor: manual`, set in-process, never from a payload) is always written. `hybrid` writes facts with confidence ≥ 0.7 and queues skills and tentative items. Changes to existing files wait as changesets (§7.2), shown as diffs. Approve/Reject in the dashboard runs the stored proposal through the curator, or applies/rejects the changeset.
- **Exclusions**: hooks do nothing at all in projects matching `excludeProjects`.

### 7.4 Mechanism review (v0.8)

A full review of the technical mechanisms against the quality bar (a healthy, consistent loop for any user or project) found three that needed a redesign and nine defects. Each has a regression test (`test/v08.test.mjs` and the updated suites).

| Finding | Before | Now |
|---|---|---|
| Additions could change meaning | An "addition" was any edit removing at most one word, so "Run X" to "Never run X" was written without approval | Only a pure insertion is an addition; any rewrite is a correction (§7.2, Validate) |
| In-session patches were not validated | The `learn` skill's patches were written as given; only the model's own `corrects` flag made them wait | The same validator as the editor; a rewrite waits for the user |
| Parallel evaluations lost learnings | Two processes could compose the same file at once and supersede each other's changeset; an unfit in-session edit created a second pending changeset | Single-consumer queue with a lease; re-check before saving; one pending change per file |
| The profile lost hand edits | Every write re-rendered `user.md` from its bullets, dropping prose, extra sections and multi-line bullets | Writes touch only the bullet lines they change |
| Secrets could slip in | The check compared the whole file before and after, so a file that already looked like it had a secret let a new one through | The check runs on the added text |
| Undo was coarse | Undo refused when the file changed at all, and per-file learning ids made "undo this learning" revert whatever was last | Line-level revert among later edits; undo per changeset (batch) |
| Three memory-dir resolvers | Curator, knowledge index and reviewer inventory computed the project's memory directory differently; a worktree got its own | One resolver, as documented by Claude Code (repository, worktrees shared, `autoMemoryDirectory`) |
| Ancestor CLAUDE.md unseen | The screen did not see CLAUDE.md files above the working directory, which Claude Code loads | They are indexed |
| Long sessions lost their middle | A tail over 80k characters kept its start and end only | Reviewed in parts |
| Budget checked once | Only before the reviewer call; screening, editing and consolidation could run past it | Checked before every call; cost recorded per call |
| Notices crossed projects | A notice from project A was injected into the next session of any project | Delivered to the same project (maintenance notices anywhere) |
| Merges could vanish | A proposal merged into one the same pass dropped disappeared with it | A merge follows its chain: it shares the target's drop or fix verdict with the reason, or is kept when the target is not saved |

**Kept as is**, because they hold up: capture through exec-form async hooks with a recursion guard; the per-session cursor (each segment reviewed once); isolated `--safe-mode` model calls; screen, ground, editor and validate as separate stages; changesets per file re-applied to the current text on approval; the ledger; conflicts handed to the user; one rubric for every path.

**Measured, not changed**: Sonnet as the evaluation model scored the same as Haiku on the synthetic suite (12/12, then 15/15 with three cases taken from real mistakes) at about 15 times the cost, so Haiku stays the default and `judge_model` lets a user choose. The suite is close to saturated; new cases should come from real disagreements (`--replay`).

**Open question**: the loop's value is not yet shown by the correction-rate metric (§9.2) on a large enough sample. Measuring that comes ahead of new mechanisms. Since v0.24 it can be measured against a control group instead of against the past (§9.2). One comparison is still missing and cannot be made from a cloud session, where Claude Code's own auto memory is off: what the native memory alone would have captured from the same sessions.

### 7.5 Routing: where a learning belongs (v0.16)

Until v0.15 *where* was decided before anything checked it, and in three ways: in session Claude picked a `kind` from a table in the `learn` skill, the curator mapped it mechanically (anything global became a line for the global CLAUDE.md), and only the end-of-session path had a screen that knew the owners. So "remember that I prefer X", the most common explicit request, landed by default in the one destination that costs context in every session and always waits for approval, even when X was about commits and a commit skill existed.

**One order, everywhere** (`scripts/router.mjs`, `DESTINATIONS`, injected verbatim into the reviewer and the screen and kept in step with the `learn` skill by `test/router.test.mjs`), most specific first:

1. the skill, rule file or CLAUDE.md that already owns the topic (a patch);
2. a project memory, when the fact only holds in one project;
3. a preference valid everywhere that matters for certain files: a user rule with `paths`;
4. a preference valid everywhere that matters for one topic: a personal skill for that topic;
5. the global CLAUDE.md, only for what is relevant in every session whatever the task.

**A home for topical preferences** (kind `preference`, with `topic` and optional `paths`). Claude Code has no cross-project auto memory, a user rule without `paths` loads in every session like CLAUDE.md, and the only mechanism that loads by topic is a skill. So: with `paths`, the preference is a line in `~/.claude/rules/learned-<topic>.md` (frontmatter `paths`, loaded when Claude touches matching files); without, a line in `~/.claude/skills/learned-prefs-<topic>/SKILL.md` (`user-invocable: false`; its description says when it applies; counts against the learned-skill budget). Preferences on the same topic share one file: the first creates it, the next ones are additions, a repeated one is a `duplicate`. Both are files Ouroboros creates, so they follow the autonomy setting like any learned skill. A rule file is "written by people" only when a person wrote it: `needsApproval` exempts a rule file the ledger shows Ouroboros created (`ownFile`, set by code from `learnings`, never taken from a proposal); corrections still wait.

**The owner check in session.** The end-of-session path has the screen; in session nothing looked. Now `curator.mjs apply` (the CLI the `learn` skill runs) looks for skills, rule files and CLAUDE.md files that own a new item (`findOwners`), in two ways: by **topic** (a preference's `topic` is the name of a skill or rule file: "commits" → skill `commit`, which owns it even when no word is shared with what it says today), and by **content** (a passage shares at least half of the statement's distinct terms, three at least, so an unrelated file never blocks). The search engine only ranks the passages. v0.16 also required an absolute BM25 score, which depends on how much knowledge exists: the first run against the real model, on a setup with three files, found no owner for a line the commit skill already had, and a duplicate preference skill was created (fixed in v0.20.1). A hit answers `has_owner` with the file and the excerpt; Claude reads it and re-submits a patch, or the same item with `owner_checked` when the topic belongs elsewhere. Same pattern as `duplicate`: the model merges, the curator guards. User-level rules (`~/.claude/rules`) are indexed as knowledge, which they were not.

### 7.6 Mechanism review II (v0.23)

A second review of the mechanisms, this time by reproducing each suspicion in a throwaway directory and against a live Claude Code session before calling it a defect. Each row has a regression test in `test/v023.test.mjs` (or the updated suites).

| Finding | Before | Now |
|---|---|---|
| Daily maintenance never ran | The hook stamped `maintenance_at`, then the worker read "ran recently" and left | The worker claims the run atomically; the hook only starts it (§7.3) |
| `~` skipped the CLAUDE.md approval | The always-approve check looked only at absolute targets; the write expanded `~` | Targets are resolved once, before any check (§7) |
| A partial review skipped the rest | One part of two read, cursor moved to the end, review marked `ok` | The cursor stops at the first unread part; the session waits and is finished later; failed and unaffordable reviews too (§6.3) |
| "Addition" meant "the old words are still there" | "do not" in front of a rule, or a clause after it, was an addition written without approval | An addition adds whole lines; anything inside a line is a correction (§7.2) |
| Early reviews on everyday work | Red, edit, green on `npm test`, or a flaky command retried, asked for a full-context review | Only a changed command, or another command in between, with no file written (§6.2) |
| In-session cost had no limit | Recorded at zero cost, outside `monthly_budget_usd`, whatever the context size | Skipped above `inloop_review_max_context`; the budget's description says what it covers (§6.2) |
| Any `node` command ran unprompted | Skills declared `allowed-tools: Bash(node:*)`: `node -e …` was pre-approved in a turn the Stop hook can start, and `curator.mjs approve` let Claude act as the user | Each skill pre-approves only its own script; `curator.mjs` has no approve, reject or confirm command (decisions go through `inbox.mjs`, which a learning turn does not pre-approve) |
| Evidence "anchored" on any recovery | With a recovery recorded, an item that cited no user turn was written; a global skill came from two small-model calls over a digest | Items that cite no user turn, and new skills from the end-of-session reviewer, wait for the user (§6.3) |
| Secrets in plain sight | A connection string with its password, a Google key, a bearer token and "the password is …" passed the filter | More token shapes, credentials in URLs, values after "is"; references such as `$TOKEN` or `process.env.X` no longer blocked (`curator.containsSecret`) |
| Two prompts behind one rate | "Before" asked for corrections and candidates in one call, "after" for corrections only | The instrument's call in every mode (§9.2) |
| Turns nobody typed | Scheduled tasks and subagent reports advanced `review_every_turns` | Checked against the transcript before asking (§6.2) |
| Deleted files stayed "learned" | See §7.3 | `removed`, with the deletion remembered |

What a live session confirmed as it was: the Stop-hook request continues the conversation, Claude runs the `learn` skill and closes with the result line, the cursor moves only then, and the review's own turns are not counted as the user's.

**Limits that remain, stated.** The narrowed `allowed-tools` rule matches a command line, not a program: it stops the easy cases (`node -e`), not a command built to look like the skill's. The secret filter is a list of shapes; the rubric's "no secrets" rule, applied by a model, is the other half. And nothing in code proves a cited user turn supports an item: the rule above only decides who looks at it first.

### 7.7 Mechanism review III (v0.25)

A third review, of correctness and of whether the value is delivered, on v0.24.0. The code was read in full and the loop was run for real: nine sessions of the installed Claude Code (2.1.322) with the plugin loaded, Haiku as the model and an isolated configuration directory, plus reproductions in throwaway directories with a stand-in model where the model's behavior was not the point. | M18 Daily buckets | After the autumn clock change there was no bucket for today (29 in 30 days); where the clock skips midnight, none for the first hour | One bucket per local calendar day (§9.2) |

| M22 Hits | A skill matched by name only, over a different set of sessions than the share divides by: 9 of 10 sessions for a skill never used, "300% · 3 of 1 session" | Matched by scope (a personal skill anywhere, a project skill in its project; a memory by path), over the sessions that started in the period (§9.2) |
| Approval that wrote nothing | A refused approval (index full, error) consumed the entry as `approved_over_budget` and emptied the inbox | The entry keeps waiting, with the reason (§7.2) |

| Inbox skill invocable by the model | A turn the Stop hook starts could load `inbox`, which pre-approves `inbox.mjs approve` | It opens only when the user types it (§9.3) |

| Metrics defined and never built | §9.2 listed utilization rate, cost per hit and a 7-day average, and §8 an `is_reviewer` column; the chart drew each day's raw ratio, and no screen showed what in-session reviews yield | The 7-day average is built; the two others are withdrawn and the column was never in the schema (§9.2, §12); an in-session yield panel is added (§9.2) |

**What a live session confirmed.** The loop closes end to end on Claude Code 2.1.322: a rule taught in one session ("use pnpm, never npm") was saved as a memory and applied in the next (`pnpm add left-pad`) when auto memory is on; a topical preference skill and a path-scoped rule were applied when their topic came up; the reviewer call with `--safe-mode` works as the code expects (`structured_output`, `usage` and `total_cost_usd` present; US$ 0.0006 to 0.0012 a call; the detached worker survives the end of the session); the synchronous hooks took 40 to 85 ms. The real-model suites scored 36/36 (`eval.mjs --sessions --runs 3`) and 16/16 (`--synthetic`). These runs are those of the review, on v0.24.0; the fixes are covered by their regression tests, whose transcripts are built to look like the real ones, and were not run live again.

**Limits that remain, stated.**

- **Whole-line additions the validator still accepts** (`textdiff.joinsExisting`): a word on a line of its own above a sentence; a heading placed above an existing list; a new parent item above existing sub-items; an unindented line right under a sentence or item (in a plain-text file it is a new line; markdown reads it as a lazy continuation, which `appendToSection` avoids by starting a paragraph, but a hand-written edit is not stopped); an indented continuation after a blank line; and a lead-in that does not end in a colon ("Rules to follow"). Together with the earlier limit that the secret filter is a list of shapes, the rubric and the user's review of the diff are the other half.
- **The approval rate infers who decided.** The ledger records the actor of a write, not of a decision; a write by `manual` within 10 seconds of the decision is counted as the user's. A decision and an automatic write that land that close together are confused,.
- **The fork marker is an assumption.** Claude Code's `forkedFrom.sessionId` on a copied entry was not seen in a real fork transcript. What was verified is that the copied entries keep their original timestamps and the fork's new id, which is what the main rule uses; the marker only serves a session Ouroboros never saw start.
- **Hits are a lower bound.** A rule followed from the memory index, a path-scoped rule and a line in a CLAUDE.md leave no event, and a skill matched by name in a project other than its own is not counted. This is also why utilization rate and cost per hit were withdrawn: one is understated and the other overstated by it.
- **The 95% interval is approximate.** It treats every turn as independent; corrections cluster by session, so the true interval is wider. With a baseline rate of about 10 per 100 turns, 200 turns on each side give an interval of roughly ±6 points and are enough to say "unclear", not to see a 30% fall (that needs about 1,350 turns per side, more if the corrections cluster). The baseline rate used for that estimate is an assumption, not a measurement.
- **A held learning holds back the others.** A change takes the strictest autonomy among its learnings, so an anchored learning for the same file waits with the held one until the user decides.
- **Knowledge › Skills** still lists a worktree's copy of a skill as a row of its own; the uses are attributed by project and the Health meter counts a skill once per repository, but the list is not merged.
- **Auto memory detection** follows the environment and the local, project and user settings; managed policy settings and `--settings` files are not read, so there it can say "on" when Claude Code does not load it, and a `memory_dir` that only those settings name is ignored with a warning.
- **A session idle for 6 hours is taken as ended.** If it was only paused, its cursors make the next review read only what came after; a session older than 7 days is left to a backfill.
- **Not exercised:** Windows and macOS (Linux only); the live sessions used Haiku in headless mode, one run per scenario, with no statistical value; the race between two processes in `applyChangeset` and the launcher's reuse of `dashboard.json` were only read.

## 8. Data model (`events.db`)

```sql
sessions  (id, project, cwd, transcript_path, started_at, ended_at, turns, tool_calls,
           turns_at_last_review, review_cursor, queued, reviewed_at, control)
          -- control: a session of a control project (measured, never learned from; §9.2)
events    (id, session_id, agent_id, ts, kind, payload_json)
          -- kind: turn | tool_call | tool_fail | recovery | long_turn
          --       | skill_used | memory_read | memory_write | review_requested | review_skipped | miss | session_start | session_end
          --       | review_unsaved (v0.25: the first turn an in-session review could not save, §6.2)
          -- session_start: target = the source (startup | resume | clear | compact | fork); session_end: target = the reason,
          --   "no SessionEnd: idle over 6 h" for a session the sweep took as ended (§6.3)
learnings (id, kind, scope, project, path, title, confidence, status,
           trigger, origin_session, created_at, updated_at, uses, last_used_at, pinned)
          -- status: active | archived | reverted | removed (file deleted outside Ouroboros, §7.3)
writes    (id, batch, learning_id, ts, op, actor, session_id, file, before, after, reverted_at, title, why)
          -- title/why: what the batch learned and where it came from (v0.8.2); the learn skill passes the session id
          -- op: create | patch | archive | revert | cleanup (index line of a deleted memory) ; actor: inloop | background | requested | manual | native
reviews   (id, session_id, mode, trigger, model, turns_reviewed, corrections, learned, patched,
           input_tokens, output_tokens, cache_tokens, cost_usd, ts)
          -- mode: inloop | background | measure | corrections | manual ; instrument: 'corrections' on the rows the correction rate counts
candidates (id, review_id, session_id, kind, title, summary, evidence, confidence, outcome, payload,
            note, claim, target, changeset_id, triaged_at, decided_at, quotes, ...)
          -- quotes: the user's own words in the turns the evidence cites ("USER #12"), JSON [{ n, text }]
          -- outcome: queued | created | patched | duplicate | dropped | merged | suggested
          --          | dismissed | rejected_by_user | over_budget | error
changesets (id, file, kind, base_hash, edits, corrects, status, note, cost_usd, created_at, decided_at, learning_id, batch)
          -- status: pending | applied | rejected | superseded | stale | reverted
notices   (id, ts, session_id, project, text, delivered_at)   -- project NULL: any session
observations (id, session_id, text, ts, closed_at)   -- noticed by a review, not settled yet (§6.5)
meta      (key, value)   -- markers and the evaluation lease (lease:evaluate)
```

`sessions.queue_state`: queued | running | done | skipped | failed | waiting (v0.23: a review to finish later, §6.3). A session the sweep takes as ended gets `ended_at` = its last event and an `end_reason` (v0.25). `reviews.status` for an in-session review: ok | skipped | failed; a skipped one carries its reason in `detail` ("could not save: …", the context limit, no result line). `fail_streaks` (the failures of a command still open in a turn) also holds, since v0.23, the first command text and the files written and commands run meanwhile.

Candidate outcomes added in v0.8: `pending` (recorded, not evaluated yet) and `undone` (applied, then undone by the user); `conflict` (§7.2). Results of `curator.mjs apply` and the inbox gained `decided` (the proposal was decided while it was being prepared; nothing queued) and `changed` (the learning is part of a change now, §9.3). A candidate's payload keeps what bounds the queue and links its stand-ins: `screen_misses` and `editor_misses` (§7.2), `autonomy` of the claim, `interim` and `interims` (stand-in memories), `retired` (those approval retired, for undo), `restored` and `confirmed`.

WAL + `busy_timeout` for concurrent sessions. Versioned migrations in `db.mjs`. The daily maintenance deletes capture events older than 400 days (more than any range the dashboard shows), except `skill_used` and `memory_read`, which back the all-time use counts. The ledger is never pruned: undo needs it.

## 9. Dashboard

`/ouroboros:dashboard` starts `node dashboard/server.mjs` on `127.0.0.1:4747` (configurable port) and opens the browser. Build-free HTML/JS, hand-rolled SVG charts, light/dark theme, English UI. The launcher reuses a running server (`dashboard.json` in the data dir) or starts a detached one that shuts down after 4 h idle. Reads are GET-only; writes go to `POST /api/action`, which requires the per-start token (served by `GET /api/token`, readable only by the page's own origin), a same-origin `Origin` and a JSON body. Every request passes a `Host` check (anti DNS-rebinding), and every response carries the strict CSP and forbids framing (`X-Frame-Options: DENY`, `frame-ancestors 'none'`, v0.25: a click inside another site's frame acted as the user). The URL is built from the validated host, so a target such as `//` or `/\` is a path and not a new authority, and a handler that throws answers 500 instead of stopping the server. The page fetches the token again and retries once when the server was restarted under it. The launcher recognizes its own server by the data directory the ping reports, and restarts it using the pid the ping reports, so another install's server on the same port, or a stale file, is left alone.

### 9.1 Screens

One page per question, in a sticky top bar; the Inbox carries a count of what waits for the user, and the dashboard opens on it whenever something does.

| Page | Question | Content |
|---|---|---|
| **Inbox** | What needs my decision? | Entries grouped by project, then by target file (new items without one by kind; suggested fixes together), in `inbox.mjs`'s order: conflicts (a learning vs a written rule: "it is a new rule" / "keep the current rule"), changes to files (one diff per file with the learnings behind it; approve, reject, remove one learning), new items, suggested fixes. A group shows its first 20 entries with "Load more"; bulk approve/reject per group and for the whole filter; "check against knowledge" |
| **Overview** | Is learning working? | Corrections per 100 turns before vs after learning with the delta and a sentence the API composes (§9.2: baseline, 200 turns per side, 95% interval), the same against control projects, learned count, sessions opening a learning, misses, month cost vs budget; trend charts (a 7-day average) with the "learning on" marker; recently learned. Control sessions are in none of it |
| **Knowledge** | What does Claude know? | **Learned**: one row per thing learned (each ledger batch), not per file: what it says (the title the writer gave, or the first sentence it added), why (the evidence, or the learnings of an approved change), where, from which session and how, what it saved or changed (a diff that opens on click), how often the file was used; actions Undo (only that change, later edits stay), Archive (only what Ouroboros created), Keep; undone rows behind a toggle next to the filter. Then every skill (personal, project and plugin skills in collapsible groups), memory (grouped by project) and instruction file, sortable by name, uses, last use or date; and **Graph** (§9.4) |
| **Activity** | What happened? | Sessions, reviews (with cost), proposals and their outcome (filter by kind, outcome, period), what the knowledge check dropped (restorable), corrections; sortable by date; on a narrow screen each row is a labelled card |

The Inbox page and the `inbox` skill (§9.3) share `scripts/inbox.mjs`: the same entries, the same decisions. Every count of what waits (the Inbox badge, System, the SessionStart hint) uses one rule, `inboxCounts` in `hook.mjs`, the same as `inboxEntries`.

**Lists at scale (v0.10).** Nothing is cut silently. Every list route returns `{ rows, total }` and takes `limit` (50 by default), `offset`, `q` (a substring of the row's text, matched in SQL), `project` and, where they apply, `kind`, `outcome`, `days`, `sort` and `dir`; the page shows "Showing 50 of 1,240" with "Load more", and counts come from `total`. Grouped lists (the inbox, the inventory) return each group's total and first rows, and `group` pages through one group. Knowledge › Learned builds diffs only for the page it returns. Bulk decisions take a filter (`{ project }` or `{ group }`) and the count the user confirmed (`expect`, required since v0.25: without it, or with a filter that cannot be read, nothing is decided and the filter never widens to the whole inbox); the server resolves the filter to entries and decides nothing when the count no longer matches.

**Projects.** One key everywhere since v0.18 (`paths.projectIdFor`): until then the dashboard and auto memory used the repository while the hooks keyed sessions, proposals, changes and notices by the session's folder, so a notice or an inbox hint from a session in a worktree or a subfolder never reached a session in the main checkout, a project skill learned in a worktree was written into the worktree (and lost with it), and a change proposed for a worktree's CLAUDE.md went stale forever once the worktree was removed. Now sessions, candidates, changesets and notices carry the repository's key (old rows are re-keyed once at `SessionStart`, from the folder they recorded); knowledge files are read from, and written to, the main checkout (`paths.stableDir`); and a change waiting for a file that no longer exists is closed with that reason instead of retried. A project is a repository's main checkout (so its worktrees and subfolders count as one) or, outside git, the session's folder; it is named after that folder, `~` for the home folder, and names that collide show the path. A learning belongs to the repository its file lives in, else to its session's project. The `projects` route lists them, and one Project filter is shared by Inbox, Knowledge and Activity.

**Page state in the URL.** `#<page>[/<list or anchor>][?filters]`, e.g. `#knowledge/learned?q=deploy&project=…` or `#activity/proposals?kind=skill&outcome=dropped&days=90`: refresh, back and shared links restore the page. Inbox anchors (`#inbox/p-<project>`) scroll within the page. Typing in a filter is debounced and updates only the list (the field stays mounted; stale responses are dropped). After an action focus goes to the control that was used, or to the next entry; re-renders keep the scroll position and open sections, and the Overview refreshes every minute only when its data changed. A request that fails empties only its own section.

Visual system: warm neutrals with one blue accent (primary actions, selection, data; filled surfaces under white text use a deeper `--accent-fill` for 4.5:1 in both themes), system sans, light and dark from the same tokens; lists and tables over card grids, cards only for decisions; one stroke icon set drawn in `app.js`; status always pairs a color with a word.

### 9.2 Metrics (definitions)

| Metric | Definition |
|---|---|
| Correction rate | Σ `reviews.corrections` ÷ Σ `reviews.turns_reviewed` over the reviews of **one instrument** (`reviews.instrument = 'corrections'`), 7-day moving average. Until v0.16 "before" was the small model reading whole sessions with one prompt, and "after" mixed Claude reporting on itself in the periodic review with the small model reading only tails with another prompt: not comparable. Now every figure comes from the same reading: one definition of a correction (`CORRECTIONS_RULES`), the reviewer model, the whole session, and since v0.23 the same call: a corrections-only call at session end (`mode = 'corrections'`, about the cost of one review), with learning on or off. From v0.17 to v0.22 measure-mode reviews (learning off, measure backfills) counted corrections in the same call that listed candidates: the same rules, another prompt. Baseline rows measured then are kept as they are; `eval.mjs --sessions` scores the one prompt that now reads both sides. A session whose measurement did not complete is not counted, and is measured again if its review is finished later. A compaction summary is not a turn, a fork's copy of its parent's turns is skipped, a session that never got a `SessionEnd` is measured once it has been idle for 6 hours, and control sessions are in neither the trend nor the baseline (§6.3, v0.25). What the learning reviews count themselves is shown apart (`selfReported`). The chart is the **7-day moving average**: the pooled rate of the day and the six before it (corrections over turns), not each day's own ratio, so a 2-turn day cannot stand as a bar at 50 among days at 2; days are local calendar days. **Primary value indicator**: should drop vs the phase 1 baseline |
| Verdict (v0.25) | The sentence under the Overview's figure is composed in the API (`compareArms`), not by the page. Each side needs at least 200 reviewed turns (`MIN_SAMPLE_TURNS`), the baseline too: until v0.24 only the "after" side was checked, so a baseline of 4 turns gave a green "46.0 fewer", and no baseline at all gave "Not lower yet". It states the difference and its **95% interval**, Newcombe's, built from each arm's Wilson score interval (so 0 corrections on both sides still has a width). It says *lower* or *higher* only when the whole interval lies on one side of zero; otherwise it says that no difference can be told yet and gives the interval, which includes zero. Without a baseline it says so: no session was reviewed before learning turned on, and how to get one (`/ouroboros:backfill measure`, or a project in `controlProjects`). Below the minimum it says which side is short. The control comparison uses the same rule. The interval treats every turn as independent and is approximate (§7.7) |
| Control group (v0.24) | Before and after are two periods, and between them the work, the model and the user's own habits changed too. `controlProjects` (globs in `~/.ouroboros/config.json`) names projects where Ouroboros **only measures**: no protocol at session start, no in-session review, and at session end the instrument's call plus the list of what would have been learned, nothing written (`sessions.control`, `hook.isControl`). The Overview sets the two arms side by side over the same days, from the first control session on, and keeps control sessions out of the before/after figures, the trend, the session counts and the fixed overhead (they receive no injection); it judges nothing below 200 turns on each side, and with the same interval as above. Limits, stated: projects differ (swap them after a few weeks to cancel that), and what Ouroboros saved for every project (learned skills, the global CLAUDE.md) still loads in a control project, so the difference measured is that of project-level learning, a lower bound. Unlike `excludeProjects`, where the hooks do nothing at all |
| Misses | Proposals with `repeats`, counted in the selected period — the user had to repeat something already learned (memory failed: not loaded, poor description, or ignored). Each one is also counted on the learning it names (`learnings.misses`, §7.3) |
| Hits | Sessions with ≥ 1 `skill_used`/`memory_read` of a learned item ("Sessions opening a learning" in the UI), out of the sessions that started in the same period, control sessions excluded. A use belongs to the item it is: a personal skill by name in any session, a project skill only in sessions of its project, a memory by its path; the uses shown in Knowledge › Skills are attributed the same way. A lower bound on use: a rule followed from the memory index, a path-scoped rule and a line in a CLAUDE.md leave no event |
| Approval rate | Decisions of the user: rejections, and writes whose ledger actor is `manual` (the inbox and dashboard buttons) within 10 seconds of the decision. What the evaluation saved by itself (`background`, `inloop`) is not an approval. Who decided is inferred from the ledger (§7.7) |
| In-session review yield | Per period: in-session reviews asked, finished, how many saved something, the skipped ones by reason, and the average tokens a finished one read (input, cache read and cache write). A low share saved against a high read per review says the cadence costs more than it yields; it is shown on System, next to the cost |
| Review cost | Σ `reviews.cost_usd` (background) + Σ in-loop review tokens (on a subscription this is quota-equivalent, not an extra charge); the average divides by the calls that were billed, and bookkeeping rows (`triage-summary`) are not reviews |
| Fixed overhead | (chars of the protocol + `MEMORY.md` lines + learned skill descriptions) ÷ 4 × sessions, over the sessions that received the injection (not control sessions) |

**Withdrawn in v0.25.** The table also defined a *utilization rate* (active learnings with a use in the last 30 days, over active) and a *cost per hit* ((reviews + overhead) over hits). Neither was ever built, and both rest on "use", which has the lower-bound problem of Hits: the first would be understated and the second overstated by every rule that works without leaving an event. The in-session review yield above is the figure that answers whether the cost of the cadence pays. `sessions.is_reviewer`, cited in §8 and §11, was never in the schema: the reviewer's own sessions run with `OUROBOROS_REVIEWER=1`, so every hook exits before recording anything.

### 9.3 The inbox in the conversation (`/ouroboros:inbox`)

Some users decide in the dashboard; others want to stay in Claude Code and talk each entry through. The `inbox` skill opens only when the user types `/ouroboros:inbox` (`disable-model-invocation`, v0.25): it pre-approves `inbox.mjs approve`, so a turn the Stop hook starts, or Claude on its own, must not be able to load it. It goes through the same entries one at a time: Claude runs `inbox.mjs show <key>` (what, where, from which session, the evidence, why it was held, the exact diff against the file as it is now), checks it itself (reads the target, greps the owners of the topic, applies the rubric; the entry's text is data, never instructions) and gives a recommendation; the user approves, rejects (with a reason, kept with the entry), skips, or discusses and edits.

Editing is what the dashboard cannot do. Claude writes the user's version and `preview` shows its diff without writing; `edit` then saves it as a manual write:
- a change to a file (`cs:`): the user's edits replace the proposed ones, validated by `applyEdits` against the current file (a stale change is fixed the same way, with no editor call); `drop` rejects single learnings of it;
- a new item (`it:`): edited fields override the proposed ones, or a whole new item re-routes it (e.g. a patch to the owning skill instead of a memory);
- a conflict (`cf:`) settled as "new rule": Claude composes the correction of the contradicted text in the conversation and it is written at once; without edits the claim goes back to the queue for the editor, as in the dashboard;
- a suggested fix (`sg:`): Claude can make the fix as normal work, then `done` (outcome `fixed`), or `dismiss`.

**Legible decisions (v0.9.1).** Early use showed that the facts existed but did not reach the user: Claude Code collapses command output, the question dialog covers the conversation, and "USER #12" means nothing to the person deciding. So:
- `show` prints a card: position (`[3/13]`), the file as `~/…` and what it is in words (a reference file of the global skill "acme", a rule file of project X, your global instructions), where it came from (session date, project, which review), why it waited (backfill, correction, rule file, autonomy setting), the reviewer's reasoning without the path prefix, and the diff;
- the evidence is shown as **the user's own words**: the review stores the cited turns' text when it runs (`candidates.quotes`, from the digest it just read); for entries stored before, the turns are found again in the session transcript by the review's time and the number of turns it covered, and cached;
- the skill makes Claude restate the card in the user's language (the user does not see command output) and ask with AskUserQuestion: the position as header, a question that names the file and the change, and a `preview` on each option showing what it would do (the diff to be written, the proposed edit, "nothing is written").

**Readable diffs (v0.9.2).** Most changes add a sentence to a long Markdown line, and a line diff showed that paragraph twice, removed and added, with the change buried at its end; Claude then shortened the lines by hand with `(...)`, so the reader could not tell elided text from file text, and list items read as `- - item`. Now a line changed inside prints once as `~ …context{+added words+}[-removed words-]context…` (a word diff, cut to 40 characters of unchanged text around each change), nearby hunks print as one block (a context line is never the old version of a line the next hunk changes), and the skill makes Claude copy the printed diff verbatim, never hand-write or elide one, keep one kind of information per card field, and keep each option to this entry's decision (a related fix elsewhere is its own question afterwards).

**Decisions that cannot go wrong quietly (v0.25).** A decision acts on the entry as it is now, or says that it did not:
- `approve it:<id>` of a learning that has since become part of a change returns `changed` with the change's key and writes nothing (approving the learning used to approve the whole change: one approved, three written); if that change is closed, it says there is nothing to approve. The dashboard's card gets the same answer when the entry was re-routed between display and click.
- Approving a change no learning waits in closes it without writing. `edit` with a `drop` that is not a list, or that lists every learning, is refused before anything changes (it used to mark all rejected, answer `invalid`, and leave a change that a later `approve` wrote, "0 updates").
- `resolve` takes `new` or `keep`, in any letter case; anything else is `invalid` and decides nothing (a mistyped "New" rejected the learning, which fed the rejection index for 180 days).
- The card of a queued item names the stand-in memories already active for it and what approving and rejecting do to them, and says why a learning waited when the editor or the screen could not handle it ("the editor of its file gave no verdict, so nothing was written and you decide").

Every decision goes through the curator, so it lands in the ledger and is undoable. SessionStart tells the user when entries wait for them (with the notices, otherwise at most once a day): "N waiting for your decision: /ouroboros:inbox (or the dashboard)".

### 9.4 Knowledge graph (Knowledge › Graph, v0.11)

What Claude knows, drawn as a graph: which skills point to which, which memories link to each other, what belongs to which project, what is used together, and what stands alone. Hermes Agent shows a memory graph; Claude Code's own auto memory already writes `[[name]]` links between memories, which nothing displayed before.

**Derived, never stored.** `scripts/graph.mjs` builds it on request from the same files the knowledge check reads (`knowledgeFiles` of every known project, minus sources of truth), every memory directory and the plugin skills, plus the usage events. No new table, no new file, nothing written. The `graph` API route caches it like the inventory (5 s).

| Nodes | Edges (strongest evidence first) |
|---|---|
| skills, their reference files, memories, CLAUDE.md files, rule files; one hub per project | **link** (`[[name]]` resolved in the memory's own folder first, or a relative markdown link to another node); **mention** (a file names a skill: a hyphenated or `plugin:` name as a whole token, a plain-word name only as code, a `/command` or next to "skill", since `deploy` or `run` as words mean something else); **contains** (a skill and its reference files); **used** (used or read in the same sessions, at least twice); **similar** (TF-IDF cosine ≥ 0.3, top 2 per item, only between items not otherwise related: a hint, drawn dashed); **belongs** (item → project) |

A `[[link]]` that resolves to nothing is reported as a **broken link** on its file. Items with no link, mention, containment or shared use are **unconnected** (candidates to link, merge or retire). Plugin skills appear only when used or named by a non-plugin file, unless the user asks for all of them. The Project filter keeps that project's items, what they relate to one edge away (so a global skill a project memory names stays) and its hub.

**Drawing (v0.13: D3).** Until v0.12 Ouroboros drew the graph with an in-house force layout; it worked but read as flat and static, and the camera and drag code was the costliest part to keep right. v0.13 vendors a D3 subset as `dashboard/public/d3.min.js` (d3-force, d3-zoom, d3-drag, d3-selection, d3-transition and d3-ease with their own dependencies, about 70 KB, ISC license in its header), imported by `app.js` as an ES module. It is served from our origin, so the strict CSP (`script-src 'self'`) and offline use are unchanged, and it lives at the top of `public/` so the server's code fingerprint sees it. To rebuild it: in a scratch folder, `npm i d3-force@3 d3-zoom@3 d3-drag@3 d3-selection@3 d3-transition@3 d3-ease@3 esbuild`, an entry file that re-exports the functions `app.js` imports, then `esbuild entry.js --bundle --format=esm --minify --legal-comments=none`, and prepend the header with the versions and the license.

The drawing is SVG styled by CSS (theme variables, classes for state), so everything except layout, camera and drag stays ours. The layout unfolds on screen from a tight spiral while the camera follows it until the user takes over; items pop in, and items Ouroboros wrote or changed breathe (a pulsing halo). Dragging an item keeps the layout warm, so its neighbors follow. d3-zoom owns pan, wheel and pinch; selecting an item (in the drawing or the panel) glides the view to it and its neighbors, and Fit glides back to everything. A dot grid moves with the view. Relations are drawn as slight curves (structure — project, contains — stays straight), links and mentions take the color of the item they start from, and the connections of the hovered or selected item flow from source to target. Skills are always labelled and the layout keeps room for their names; a name that would overlap a bigger or better connected item's waits for zoom, hover or selection; other items are named on zoom, hover or selection. Hovering or selecting dims everything except the item and its neighbors. Under `prefers-reduced-motion` the layout is computed at once and no transition or animation runs. Positions are kept while the page is open.

**Legible by default (v0.14).** Drawing everything (about a hundred items, half of them one skill's reference files) gave a hairball. The page now draws less than the data holds, and every cut can be undone:
- **Reference files fold into their skill.** A folded skill wears a dashed ring and the number of files it holds; their connections are drawn from the skill. Selecting the skill (or one of its files, from the panel or the search) redraws with that skill open and glides there; selecting something else folds it again. "Open every skill" opens them all (`refs=all`).
- **Projects are regions.** Each project gets a fixed place on an ellipse (by name, from the whole data, so filters do not move it); its items are pulled there and a soft circle around its hub, named on top, marks it. What applies everywhere sits in the middle. Projects whose items are all unconnected wait on an outer ring. An item its links pull far from its hub stays outside the region rather than stretching it.
- **Fewer lines.** "Similar" (a hint) and "Project" (the regions say it) are off by default (`off=none` turns every type on); a folded file's connections merge into one line per pair and type.
- **Unconnected items wait in the panel**, which says how many are not drawn and can draw them ("Unconnected items", `lonely=show`). Selecting one from the panel draws it.

A redraw (a filter, a skill opening or closing) keeps the view and every placed item's position, so only what changed moves.

The side panel is the accessible path through the same data: with nothing selected it summarizes, lists the unconnected items and broken links, and browses every item by kind; a selected item shows its path, description, use, broken links and its connections grouped by how they read from its side ("Links to", "Named by", "Contains", "Used together with"…), each a button to move there, plus a link to it in the Knowledge lists. Filters for kinds and edge types, the search (highlights matches; one match selects it) and the selection live in the URL (`#knowledge/graph?hide=memory&off=none&refs=all&lonely=show&sel=…`).

Phase 1 is read-only on purpose. Later, the same graph could drive behavior: write `[[links]]` when Ouroboros creates a memory, turn broken links into suggested fixes and unconnected unused items into decay candidates, and link sources of truth to their owners so a change in a source re-checks the owners (the known gap in §7.2). Those wait until the correction-rate metric shows the loop's value (§7.4).

## 10. Distribution

- Public GitHub repository (MIT) that is its own marketplace (`.claude-plugin/marketplace.json`).
- Install: `/plugin marketplace add lucamartins/ouroboros` → `/plugin install ouroboros@ouroboros`.
- `claude plugin validate --strict` in CI.
- On Windows the reviewer runs `claude.exe` when the PATH has one (the native install), else the CLI script behind npm's `claude.cmd` shim with the current Node: Node cannot spawn a `.cmd` without a shell, and a shell would mangle the JSON schema argument (`resolveClaude`; unit-tested, not yet exercised on a real Windows npm install).
- Declared requirement: Node ≥ 22.13 on PATH. `SessionStart` checks the version and, if missing, warns once and disables the hooks silently.

## 11. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Memory pollution (auto mode) | Quality filters, dedupe, hard limits with consolidation, archive on disuse, undo |
| Infinite `Stop` loop | `stop_hook_active`; turn-count cadence; cursor only advances on a completed review |
| Learning latency | A correction is learned at most N turns later, still in the same session; the transcript stays on disk, so compaction loses nothing for reflection B |
| Cost of reviews with nothing to learn | Cache-read input, short output; cadence configurable; visible on the Cost screen |
| Latency | Async capture; a single Node process per event; reflection B off the critical path |
| `SessionEnd` 1.5 s budget | Only enqueues and spawns a detached worker (no `timeout` declared: plugins cannot raise the limit); orphaned queue reprocessed at the next `SessionStart`, and a session that never got a `SessionEnd` queued after 6 hours idle (§6.3) |
| Auto memory off (`--bare`, a cloud session, a setting) | `SessionStart` detects it, warns once per project and adds the learned memory index to the session context; System shows it (§5). A cloud container is also ephemeral: `events.db` and `~/.claude` do not outlive it |
| The correction rate counts what is not the user's | Compaction summaries are not turns, a fork's inherited turns are skipped, control sessions are out of the learning arm, and the verdict needs a baseline and states its interval (§6.3, §9.2) |
| Recursion (reviewer fires hooks) | `OUROBOROS_REVIEWER=1` disables everything (every hook exits before recording anything, so the reviewer's sessions are in no metric); separate `cwd` |
| Prompt injection teaching the agent | Learn only from user turns and observed outcomes; tool text never becomes a literal learning |
| Cross-project leakage | Scope-based routing; `excludeProjects` |
| Sensitive data written | Secret filter (token/key/password patterns) on the text each write adds; dashboard bound to `127.0.0.1` only |
| Concurrent evaluations | One consumer at a time (database lease); compositions re-checked before saving; writes under the write lock with an expected base text |
| The user's hand edits lost | Edits are exact fragments re-applied to the current file; undo reverts only the lines its write changed |
| Skill listing budget (~1% of context) | Cap on learned-skill count and description length; metric on the Health screen |
| Reviewer cost | Haiku, unreviewed tail only, compact digest, monthly cap |
| In-session review cost | Cached input, short output, a cadence in typed turns, early reviews only for a working path, none above `inloop_review_max_context` |
| The user deletes what was learned | The record follows the file (`removed`), and the deletion counts against saving it again (§7.3) |
| The agent approves its own proposals | Skills pre-approve only their own script; decisions are not a `curator.mjs` command; the `inbox` skill, which can approve, opens only when the user types it (v0.25). Not a hard boundary: a user who allows every Bash command has none |
| Another site drives the dashboard | `Host` and `Origin` checks, a per-start token, and no framing (`X-Frame-Options`, `frame-ancestors 'none'`); no request can stop the server (§9) |

## 12. Decisions

| Decision | Choice |
|---|---|
| Name | `ouroboros` |
| Autonomy | Automatic by default (like Hermes) for what Claude saves in session and for facts the end-of-session reviewer ties to something the user said; a new skill from that reviewer, or an item of its that cites no user turn, waits for the user (v0.23), and keeps waiting when another learning joins its change (v0.25). `hybrid`/`queue` available as options |
| Reflection | Periodic in-loop review every N turns (+ early after a turn that recovered from repeated failures, at most every 5 turns) and an end-of-session background review of the unreviewed tail |
| Context of a review | The session's learning state (what earlier reviews saved, queued, left open) goes to every review, and a tail gets the turns before its cursor as context; segments are still reviewed once (§6.5) |
| Correction rate | One instrument: a corrections-only reading of each whole session with one definition, one model and, since v0.23, one prompt in every mode; counts made by the learning reviews are shown apart (§9.2). Since v0.25 what it counts is only what a person typed in that session: not a compaction summary, not the turns a fork copied from its parent, not a control session in the learning arm |
| The verdict | Composed in the API, not the page: 200 turns on each side, the baseline included, and a 95% interval of the difference (Newcombe over Wilson). "Lower" or "higher" only when the whole interval is on one side of zero; otherwise it says no difference can be told yet. The interval is approximate because corrections cluster by session (v0.25, §9.2) |
| Measuring the value | A concurrent control group (`controlProjects`: measured, never learned from) next to the before/after comparison, which cannot tell learning from everything else that changed (§9.2). `claude plugin eval` was tried and set aside: its sandbox confines writes to the run's workspace, and the curator writes to the memory directory |
| Files a person wrote | A CLAUDE.md, a rule file and a skill Ouroboros did not create change only with the user's approval; an addition is active meanwhile as a project memory. A global CLAUDE.md that does not exist is created by the approval, not by the proposal (v0.24) |
| Auto memory off | Detected at `SessionStart` from the sources Claude Code reads. Said once per project; the learned project memories are added to the session context instead of being saved and never read; System shows the warning. Nothing is saved differently: the same files, the same ledger, only loaded another way (v0.25, §5) |
| Files a session forks or compacts | A compaction summary is not a user turn; a fork's copy of its parent's turns is skipped by reviews and by the instrument, by the entries' timestamps and, when present, Claude Code's `forkedFrom` marker. A session with no `SessionEnd` is taken as ended after 6 hours idle, up to 7 days back (v0.25, §6.3) |
| Files deleted outside Ouroboros | The record follows the file: `removed`, out of every count, remembered as a rejection for 180 days, active again if the same file returns (§7.3) |
| In-session review cost | Not in the USD budget (it is the session's own model and tokens); bounded by context size (`inloop_review_max_context`) and by asking only on typed turns and real working paths (§6.2) |
| Prompt classification | None — no regex or per-prompt classifier; corrections are counted by the reviews |
| Where a learning goes | One order of destinations for every path: owner file, project memory, path-scoped user rule, topical preference skill, global CLAUDE.md last; in session the curator answers `has_owner` when a file already speaks about the topic (§7.5) |
| Global facts | Additions to the user's global `~/.claude/CLAUDE.md`, with approval; the separate `~/.ouroboros/user.md` profile was retired in v0.12 (§3.2) |
| Subagents | Full transcripts not reviewed; only `recovery` snippets captured inside subagents; workflow agents excluded |
| In-Claude-Code panel | Not needed |
| Skill destination | Automatic routing (global vs project, with a per-repo map) |
| Repository | Public on GitHub, MIT; every file in English |
| Runtime | Node ≥ 22.13, zero dependencies |
| Judging learnings | One rubric everywhere; screen + editor must both agree before an existing file is changed; a new item needs the screen and the curator; no verdict means nothing is written |
| Changes to existing files | One changeset per file, composed with every pending learning; the model writes exact-fragment edits, code validates and applies them; re-applied to the current file on approval |
| Rules waiting for a project file | Saved at once as a project memory; approval promotes the line into the file and retires the memory, rejection keeps the memory (§7.2) |
| Refining its own memories | In `auto`, a memory Ouroboros created and nobody edited since is refined without approval, description and index line included; decided from the ledger (§7.2) |
| Additions vs corrections | Decided by code, not by the model's label: only whole lines added to a file are an addition (v0.23: text inserted inside a line is not); any rewrite is a correction and waits for the user, on both write paths |
| Reviewing the inbox | Two equal ways over one module (`inbox.mjs`): the dashboard, and `/ouroboros:inbox` in the conversation, one entry at a time, where the user can discuss and edit before approving. The skill is not model-invocable: it can approve, so only the user's own command opens it (v0.25) |
| Dashboard at scale | Server-side paging and filters on every list, the inbox grouped by project then by file, bulk decisions by filter on the server, page state in the URL (v0.10) |
| Metrics withdrawn | Utilization rate and cost per hit are not measured: both divide by "use", which has no event for a rule followed from the memory index, so one would be understated and the other overstated. Hits stay as a lower bound, and the in-session review yield (reviews that saved something over reviews, and tokens read) answers whether the cadence pays (v0.25, §9.2) |
| Evaluation model | Haiku by default (`judge_model`): on the synthetic suite Sonnet scored the same at about 15 times the cost; revisit when the suite tells them apart |
| Knowledge graph | Derived on request from the files and usage, never stored; drawn with a D3 subset vendored into `dashboard/public/` (v0.13; the in-house layout before it looked flat and static, and its camera and drag code was costly to keep right). Vendored, not fetched: the CSP and offline use hold, and there is still no `npm install`. Legible by default (v0.14): reference files fold into their skill, projects are regions, "similar" and project lines and unconnected items are off until asked for. Read-only until the loop's value is measured (§9.4) |
